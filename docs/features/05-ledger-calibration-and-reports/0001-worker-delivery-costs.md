- Worker delivery costs: `north worker-ledger --summary` includes median brief-to-landed minutes, dollars per done box and observed completed-worker concurrency by model/effort/fast and project. NorthThreads stores account, model, effort, fast and included-plan dollars; weekly readout deltas allocate dollars to token samples from active runs (input 1, cache write 1.25, cache read Opus 0.05/others 0.1, output 5). Missing measured intervals print unknown costs. `--backfill --since 2026-10-11` rereads prior runs. A fleet session is reread while its transcript changes even after its run settles, and a later finished turn replaces its outcome, report, end and minutes: its report is the latest turn with a decided outcome, so a later acknowledgement, wait or unclear reply keeps it, and a session that reported Not done while queued and Done once landed counts as one done box, and a fleet session that safe-push recorded landing in `pushes.tsv` (its session name, from the run's start until a session of that name is launched again, since the land queue may push after the session's last turn) is landed even when its transcript shows no push or it was parked mid-turn (north#255); remote ledger reads use its snapshot, never a frozen local database. `threads ingest` accepts `type=usage` readout rows and refreshes the mirror after publishing them, using the existing remote spool during outages. Senders reach the ledger host through `north threads ingest`, which reads its input and then takes an exclusive `ingest.lock` beside the ledger, waiting up to 5 s; a second ingest that cannot get it exits 75 (retry) and the sender spools the batch instead of piling up a process on the host. `north worker-ledger`'s own ingest goes through it too, so it waits behind a held lock like any sender. `ingest` makes no network call while it holds that lock: the category of a worker run whose brief names none comes from its issue labels in `north threads label-runs`, which `north worker-ledger` runs on the ledger host after each ingest (one `gh issue list` per repo with no lock held, for runs that ended in the last 3 days and are still `unknown`); on Nexus the per-repo listings took 2 to 10 s each inside the lock, a 13 s median hold and 30 s or more at worst (north#255, 2026-11-01). Every ingest on the ledger host appends one JSON line to `ingest.log` beside the ledger (pid, start and end time, `waited_ms`, `held_ms` null for a refused one, `total_ms`, exit code), so a day of traffic shows how many ingests overlapped and how long each lived.
