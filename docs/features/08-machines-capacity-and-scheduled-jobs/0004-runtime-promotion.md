- Runtime promotion: `north runtime update` (run by each `north agent-runtime-update` pass) fetches north main and, when `~/.local/state/north/current` is behind origin/main, builds it with `CARGO_PROFILE_RELEASE_INCREMENTAL=true` in one detached `worktrees/runtime-build` lane reused for every commit (the dev shell keys `RUSTFLAGS` on the checkout path, so a per-commit path would recompile every dependency) under a `runtime` capacity lease (front of the queue, never deferred by load, disk or heavy leases) (while this host is in game-reserve it instead prints `north runtime: building <short> on HOST while this host is in game-reserve`, runs `north runtime update` on the first other `[hosts.NAME]` with room by the `north capacity offload` rule and rsyncs that host's programs back, so the game never waits out a build), installs `runtimes/<sha>/north`, `verify-north` and `tree/` (a `git archive` of that commit, which scheduled jobs run harness code from), swaps `current` atomically, runs `north runtime health` and `agents sync` (each bounded to 5 minutes; `git fetch` to 2 minutes) (which projects skills, scripts and hooks from the new `tree/`, so they change only when `current` does) and swaps back if either fails, alerting the proxy; every host runs it from its own `north-runtime-follow` timer every 2 minutes, and returns before building, exporting or rooting when `current` already names origin/main; a commit whose build, health or sync failed is held back for an hour (`runtime-failed` names it), so the timer neither rebuilds it nor alerts again until then, while a deferred build (exit 75) retries on the next tick, and so does a build that capacity admission or its systemd scope stopped before cargo ran (the build passes `--timings`, and a failure that left no `cargo-timings/cargo-timing.html` newer than the build start is a refusal, not a broken commit); it keeps the previous runtime plus the 3 newest others and holds `runtime-update.lock`. Promotion roots each store path the binaries name as `runtimes/<sha>/gcroot-<store name>` (`nix-store --add-root --indirect`), so Nix garbage collection never removes what a promoted runtime loads and pruning a runtime releases its roots. A build is abandoned when `origin/main` moves past its commit (checked every 20 s; `NORTH_RUNTIME_WATCH_SECONDS` overrides) while it has run no more than half the last local build's wall time (`runtime-build-seconds`): its process group is stopped and `north runtime update` restarts on the new head. A build past that half is finished and promoted, and the same run then builds the new head, up to 5 passes before exiting 75, so landings that arrive faster than a build still move every host forward instead of livelocking. Before pulling or building, `north runtime update` reuses the live runtime's binaries for a target whose `git diff --name-only` from the live commit touches no Rust build input (`crates/`, `src/`, `.cargo/`, `Cargo.toml`, `Cargo.lock`, `build.rs`, `rust-toolchain.toml`, `flake.nix`, `flake.lock`, `bin/cargo`, and the `harness/defaults.toml`, `harness/model-catalog.toml`, `harness/model-watch-sources.toml`, `agent-machinery/file-skills.toml`, `north-data/private-checks.toml`, `north-data/expectations.toml` and `bin/threads` that sources `include_str!`), copying them into `runtimes/<sha>/` beside the new `tree/` and printing `north runtime: <short> changes no Rust build input since <live short>; reusing its binaries without a build`, but only when the live runtime is usable on this host (a host that builds only its own runtime reuses only a runtime it built itself, never one imported from another host), and main's host-aware readiness check still decides first whether a runtime is already in place; a unit test fails when a source embeds a file outside that list. A host builds a runtime only when no other host has one: `north runtime update` first pulls `runtimes/<sha>/north` and `verify-north` from each other host with an `ssh` or `deploy_ssh` destination over rsync and runs `nix-store --realise` on their store references (a pulled runtime that fails either step is discarded), then builds locally; a host whose `[hosts.NAME]` sets `builds_runtime = false` (Nexus) never builds. A host that can neither pull nor build origin/main (it does not build runtimes, its game-reserve offload found no room, or its capacity lease deferred the build) reads each peer's `current` over ssh and promotes the newest one that is an ancestor of origin/main and ahead of its own, printing `north runtime: <main> is not built anywhere yet; catching up to <short>, promoted on HOST`; it exits 75 only when no peer is ahead. `north runtime deploy HOST...` builds that runtime on the machine it runs on (the laptop, so Nexus's 3 cores never compile north), runs `nix-store --realise` over its store references on each HOST, rsyncs the programs into the HOST's `runtimes/<sha>/` and runs the shipped `north runtime update --sha SHA` there, which waits up to 10 minutes for that host's `runtime-update.lock`, skips its build and promotes exactly that commit. Each deploy step prints what it waits on (the `runtime-update.lock`, the build, `nix-store --realise`, the copy, the remote `north runtime update`) and is stopped with an error naming the step, the host and its limit (30 min for the lock, 10 for realise and copy, 15 for the remote promote; `NORTH_RUNTIME_STEP_SECONDS` overrides them), so a stuck deploy fails with its reason instead of hanging. `north runtime deploy` with no HOST ships to every other `[hosts.NAME]` that has an `ssh` destination and attempts the rest when one fails, except that a host which sets `builds_runtime = false` (Nexus) is shipped to only by a host that sets `settles_fleet = true`: elsewhere (gex45 has no ssh route to Nexus) it is left out of the plan, and the deploy prints `north runtime deploy: skipping nexus: it builds no runtime, and the host that settles the fleet ships to it`. After a landing on north's main branch, safe-push runs `north runtime follow --repo-dir DIR`; for a repository whose origin is `north` it starts `north runtime promote` (`runtime update` here, then `runtime deploy` to every declared host) in the background, logging to `runtime-follow.log`, so a landed change reaches `~/.local/state/north/current` on each fleet host with no manual step. On the host whose `[hosts.NAME]` sets `settles_fleet = true` (the laptop, the one host that reaches gex45 and Nexus), `north runtime update` runs `north runtime settle`: it updates here, ships its runtime to each deploy destination whose `current` differs, then probes every host over one ssh script for its live runtime, `capacity-watchdog.service` and `north-runtime-follow.timer` state, its north process count against `landing_north_processes_max`, and every absolute path a hook command names in `~/.claude/settings.json` and each non-stale profile `settings.json`, printing `north runtime settle: HOST: live and healthy` or its problems and writing `runtime-settle.json` with its CPU pressure avg60 and load per core recorded but not judged, since host overload is the capacity watchdog's to report. Each landing is judged once, on the first tick at least `landing_live_deadline_sec` (600) after it landed (`runtime-settle-judged` names it): a host whose runtime is not that commit or a descendant, or any problem, reopens the landing's `(north#N)` issue with the problems as a comment and fleet-sends them to the proxy and every session whose tasks name that issue. `agents sync` refuses to activate a generation that lacks a hook still registered under `~/.agents/hooks/` in those settings files, naming each missing hook and the file that registers it, and keeps the current generation.
