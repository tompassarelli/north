- Runtime promotion: the fleet runs a pinned runtime, not origin/main's HEAD. The host that settles the fleet promotes origin/main on each landing, not on a clock, and skips a landing whose commits since the pin change no runtime input (`north_base::build_inputs::runtime_input`: every path but docs, tests, examples, CI workflows and license files, with the run-time data docs still counted). One promotion runs at a time: a landing that finds one running marks itself wanted and leaves, and the running one follows origin/main again until no mark is left, so the newest head is promoted next with no spacing and no daily cap. A promotion reuses binaries already here (the live runtime or any other built or shipped one whose commit differs in no Rust build input) and otherwise builds at full parallelism; the land check builds no release runtime, so there is none of its to take. It runs the core-loop probes on the promoted runtime there, and only when they pass does `north runtime promote` or `north runtime settle` ship it to the other hosts, so a runtime that breaks the core loop is rolled back on the settling host and reaches no second one. Every other host the settling host ships to runs only the pinned runtime and never follows origin/main itself. `north runtime status` prints the pinned SHA, when it was promoted, whether it walked the spine here and since when landings that change a runtime input have waited for a promotion, read from `runtime-pins.jsonl` (or the records mirror on a host that holds another host's records). After a north landing safe-push runs `north runtime follow`, and each host's `north-runtime-follow` timer runs `north runtime update`, which pulls or builds the runtime (a build in progress always finishes), has the incoming runtime run `north check calls` against every north call on the host (system and user unit Exec lines and the store scripts they run, Claude settings hooks, and its own ssh hops to other hosts) and holds it for an hour with the live runtime kept and one proxy alarm naming the unit and line when its dispatcher lacks a verb or its table drops a subcommand the live table listed (north#825), swaps `current` (only the link moves, so a running session host keeps the runtime it started on), and swaps back with an alert to the proxy when `north runtime health` fails; for 10 min after a swap each host's tick rolls the runtime back with a proxy alarm when launch refusals (the threads ledger), session-host exits or land refusals (this host's lifecycle ledger) ran faster since the swap than over the hour before, at least twice each; a failing `agents sync` keeps the runtime, alerts once per cause and retries each tick (north#731). On the host that settles the fleet, `north runtime settle` runs the bounded core-loop probes on the promoted runtime here first and ships it to the other hosts in parallel only when it passed, then runs the probes on every host per promoted SHA, on the host itself (a sandboxed worker shell reaching the hub host, the hub fetching a repository with its credential, each repository's lander minting its push token by the credential path its running `land serve` was started with, a host with no running lander or a repository no running lander serves reported once as not applicable, and a host that cannot mint by any path paged once as a host fault with no rollback, one `--test` worker per provider the host can launch answering its first turn inside a scratch state root that carries the threads ledger `north fleet` opens and widens (north#1027), with a provider whose binary or launch key is missing reported once as not applicable rather than probed, on every host but the placement-only hub, where a launch that never reaches a worker is unrun), rolling a host back with a proxy alarm naming the failing probe and quarantining that SHA there until a newer landing (north#1022); a probe the judged runtime cannot run is unrun rather than failed, the rollback target is trusted and never judged again, and a rollback behind a held update lock defers to the promotion holding it. Each landing that changes a runtime input, promotion, walk and rollback is journaled to `runtime-pins.jsonl`, from which the scoreboard reads three bars: promotions that broke the core loop on a second host (at most 0), the slowest rollback after its swap (at most 2 min) and landing to live p90, from each such landing to the first promotion after it (at most 2 min). Deploy and settle move a host forward only (north#651). A host set `publishes_host_facts = false` has its config facts published by the settling host (north#653). See `north runtime --help`.
