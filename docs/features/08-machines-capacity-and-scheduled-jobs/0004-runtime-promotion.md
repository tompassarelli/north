- Runtime promotion: the fleet runs a pinned runtime, not origin/main's HEAD. The host that settles the fleet promotes origin/main at fixed slots, one every `runtime_promotion_slot_sec` (4 h: 00:00, 04:00 ... 20:00 UTC; no count limit rests on promotions, the canary's probes, the per-host rollback and the reviewer's read are the rule), and at once for a landing whose commit carries a `Live-fix: REASON` trailer naming what is broken on main or in the running runtime; `north runtime order --reason REASON [--commit REV]` promotes a commit already on origin/main to the settling host and every deploy host at once, as the coordinator's step on the settling host: the settling host runs its canary against the runtime before it is live and goes live only on a pass, then every other host does the same at once while the lander link follows on the settling host, whose replay runs in a unit of its own the order does not wait on (north#1183); each live host rewrites its stable pin, a failed canary leaves that host on its old runtime and names the probe, each failure is printed as it happens, every host is moved to the ordered commit even back from a newer runtime (a ship alone never moves a host back, so the order then has the runtime live there run `north runtime update --sha SHA --ordered`, which holds back a runtime the hold-back list holds there and, like `north runtime update --sha SHA`, takes a runtime live for the host that shipped it or the operator and not for a fleet worker session or an offloaded job; a host whose live runtime is from before that flag is named as one the order cannot move back until an order of a newer commit ships it a runtime that takes it) and a host that still runs another runtime is named, recorded as not live and fails the order, `north-stable-hold.service` is stopped for the run and started again, with the order marked in `runtime-order.lock` from before that stop until the unit holds the promotion lock again, so a promotion that takes the lock in either gap leaves it to the order (north#1171), and one `ordered` row per host in `runtime-pins.jsonl` names the commit, the orderer, the reason and the verdict; a fast-path promotion takes the next slot's place (docs/rationale/propagation.md, Promotion cadence). A slot promotes the newest head whose release runtime is ready, which the host has built once `runtime_slot_build_lead_sec` (10 min) before the slot, and passes when no commit since the pin changes a runtime input (`north_base::build_inputs::runtime_input`: every path but docs, tests, examples, CI workflows and license files, with the run-time data docs still counted). One promotion runs at a time under `runtime-promote.lock`, which its fetches and builds hold: a caller that finds one running dates its landing, waits for it (at most 10 min, then the next tick takes it) and reads the schedule again; between slots it prints that the head waits for its slot or a Live-fix landing and exits 0. `runtime-update.lock` covers only each swap (install, sync and going live), so a rollback waits for a swap and never for a build, and the lander link follows each runtime as soon as it is live, on a thread of its own while the promotion builds its next pass, not after its last pass. A promotion reuses binaries already here (the live runtime or any other built or shipped one whose commit differs in no Rust build input) and otherwise has the build host it reaches with the most free cores (gex45, cpx62 or cpx62b by their admission's free cores) build that exact landed commit with `north runtime build SHA` under the build host's runtime lease, takes its `north`, `verify-north` and built-from stamp, refuses them unless the stamp names that commit and the binary's hash, and journals the builder and the binary's sha256 as a `built` event in `runtime-pins.jsonl`; it builds at full parallelism here only when no build host answers or the one it chose fails, and its log line says which. The land check builds no release runtime, so there is none of its to take. It runs the core-loop probes on the promoted runtime there, plus that runtime's `verify-north` and one scratch landing on the settling host, and only when every one passes does `north runtime promote` or `north runtime settle` ship it to the other hosts, so a runtime that breaks the core loop, its verify-north or its scratch landing is rolled back on the settling host and reaches no second one. The probe list is the judged runtime's own: a promotion and an order ask `runtimes/SHA/north runtime probe list HOST` for it, so a probe a commit retires stops judging that commit and a probe a commit adds judges it from its own promotion on, and `north runtime promote` leaves the walk after its swap to the runtime it promoted (`north runtime walk`), which walks, ships and moves the lander link with its own code; a runtime older than either verb, or one that dies in its own walk, is judged and walked by the one promoting it, which says so. Since a candidate could drop a probe it should fail or empty one under its old name, an order prints, before any probe runs, the probes added, the probes removed and the probes whose script changed against the list of the runtime live on the host and keeps that line in the canary verdict's cause, and the reviewer reads it before the promotion (north#1022). Every other host the settling host ships to runs only the pinned runtime and never follows origin/main itself. `north runtime status` prints the pinned SHA, when it was promoted, whether it walked the spine here and since when landings that change a runtime input have waited for a promotion, then the promotions and fast paths of the last 24 h and the next slot, read from `runtime-pins.jsonl` (or the records mirror on a host that holds another host's records). Each promotion that falls due is journaled as a `due` event with its sha, reason (slot or fast-path) and time: a slot promotion at its slot, a fast-path one when its landing is seen. When a due promotion is not live 5 minutes later, the settling host pages the coordinator once for it and for any that fall due behind it, naming the promotion and its wait and journaling the page, while a landing waiting for its slot is on schedule and pages nothing, so a promotion stuck behind a build or a held update lock is noticed before settle fails the landing at its deadline. After a north landing safe-push runs `north runtime follow`, and each host's `north-runtime-follow` timer runs `north runtime update`, which pulls or builds the runtime (a build in progress always finishes), has the incoming runtime run `north check calls` against every north call on the host (system and user unit Exec lines and the store scripts they run, Claude settings hooks, and its own ssh hops to other hosts) and holds it for an hour with the live runtime kept and one proxy alarm naming the unit and line when its dispatcher lacks a verb or its table drops a subcommand the live table listed (north#825), swaps `current` (only the link moves, so a running session host keeps the runtime it started on), and swaps back with an alert to the proxy when `north runtime health` fails; for 10 min after a swap each host's tick rolls the runtime back with a proxy alarm naming what it counted when launch failures (a launch placement let through that failed before its session started, from the threads ledger; a launch placement refused or queued on purpose is not one), session-host exits (a host that stayed stopped for a minute, never a restart onto the new runtime nor a `vn-*` scratch host) or land refusals (this host's lifecycle ledger) ran faster since the swap than over the hour before, at least twice each; a failing `agents sync` keeps the runtime, alerts once per cause and retries each tick (north#731). On the host that settles the fleet, `north runtime settle` runs the bounded core-loop probes on the promoted runtime here first, plus its `verify-north` and one scratch landing, and ships it to the other hosts in parallel only when every one passed, then runs the probes on every host per promoted SHA, on the host itself (a sandboxed worker shell held to the sandbox's rules and, where sessions reach the hub host, one reaching it through `north capacity offload`, both served by a broker the judged runtime starts, the hub fetching a repository with its credential, each repository's lander minting its push token by the credential path its running `land serve` was started with, a host with no running lander or a repository no running lander serves reported once as not applicable, and a host that cannot mint by any path paged once as a host fault with no rollback, `north depbox run -- true` in a scratch checkout carrying the removal roots a worker command hands depbox, so depbox execs the judged runtime's north inside its sandbox as a worker's land check does (a runtime whose depbox hid that north refused every landing through it on whiterabbit on 2026-11-10, north#1068), `north runtime probe services`, which reports as a host fault with no rollback each host service (a broker, a lander, a watchdog, the offload taker) that runs a runtime older than the one the promotion replaces, since such a process follows no promotion, and counts a session process behind without failing, after first asking each on-demand host service on a runtime older than the live one (the user broker, a GitHub broker no unit keeps) to exit at its next idle moment, as a promotion also does once its runtime is live: the service loses its socket path, so its next client starts it on the live runtime, and gets a TERM once no client has been connected for 5 s, while one still serving a client after 15 s is left for the next promotion and, since no new client reaches it, is named without failing the probe, which fails for one that still takes new clients (a user broker ran a day-old runtime through some thirty promotions, north#1022), one `--test` worker per provider the host can launch answering its first turn inside a scratch state root whose threads ledger is seeded from the host's own store schema, so the probe opens the previous schema and the judged runtime widens it true` that pushes a repository), reported once as not applicable rather than probed, a Claude launch trying the account placement chose and then each account the host's own plan lists as available, and with none available unrun naming the account lines it read, on every host but the placement-only hub, where a launch that never reaches a worker is unrun), rolling a host back with a proxy alarm naming the failing probe and quarantining that SHA there until a newer landing (north#1022); a probe the judged runtime cannot run is unrun rather than failed; a failing runtime rolls back only when it does worse than its rollback target, the newest replaced runtime whose canary passed or was kept: it fails a probe the target passed, or stops at an earlier verify-north step, and a target with no walk on record is walked on those probes first; a runtime whose target fails the same probes no later, or cannot be walked, stays live as `kept`, unshipped, with the failure recorded against both and one keyed page to the proxy per host and failing step (north#1103); a rollback never marks its target trusted, and a rollback behind a held update lock defers to the promotion holding it. Each landing that changes a runtime input, due promotion, promotion, walk, rollback, canary run and per-host copy is journaled to `runtime-pins.jsonl`, from which the scoreboard reads six bars: promotions that broke the core loop on a second host (at most 0), the slowest rollback after its swap (at most 2 min), due to live p90 over 24 h, from each due promotion to the first promotion after it (at most 2 min), the runtime's age, the wait of the oldest landing no promotion has made live (at most 24 h), the canary's p90, how long the core-loop probes ran on one host (at most 60 s), and the ship p90, how long a runtime took to copy to a host as an rsync binary diff against the runtime that host runs (at most 30 s). The lander asks for a queued candidate's release runtime ahead only when its commits carry `Live-fix:`, the one landing whose promotion waits on a build. Deploy and settle move a host forward only (north#651). A host set `publishes_host_facts = false` has its config facts published by the settling host (north#653).`north runtime lag --json` prints, for every declared host and long-lived north process, the seconds it runs older than the runtime the settling host pinned (0 when it runs the pin or a runtime built on it, so a landing waiting for its slot pages nothing, and the runtime's age bar covers how far the pin is behind main); the settling host's fleet tick starts `north runtime lag --sample` at most once a minute in a scope of its own, so the reading does not stop with the stable pin; it samples the worst for the `ready-runtime-lag` bar, pages the proxy once per session episode more than `runtime_promotion_slot_sec` behind the pin (a session keeps the runtime it started on by design, so only a tool-server hours behind is an alarm), and pages by name each host service (broker, lander, watchdog, offload taker) each time it starts to lag past 5 min (north#1081, north#1022). See `north runtime --help`.
