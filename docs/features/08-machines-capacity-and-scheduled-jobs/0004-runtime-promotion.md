- Runtime promotion: the fleet runs a pinned runtime, not origin/main's HEAD. The host that settles the fleet promotes origin/main on each landing, not on a clock, and skips a landing whose commits since the pin change no runtime input (`north_base::build_inputs::runtime_input`: every path but docs, tests, examples, CI workflows and license files, with the run-time data docs still counted). One promotion runs at a time under `runtime-promote.lock`, which its fetches and builds hold: a landing that finds one running dates itself, waits for it (at most 10 min, then the next tick takes it) and follows origin/main at its newest head, so the newest head is promoted next with no spacing and no daily cap. `runtime-update.lock` covers only each swap (install, sync and going live), so a rollback waits for a swap and never for a build, and the lander link follows each runtime as soon as it is live, on a thread of its own while the promotion builds its next pass, not after its last pass. A promotion reuses binaries already here (the live runtime or any other built or shipped one whose commit differs in no Rust build input) and otherwise has the build host it reaches with the most free cores (gex45, cpx62 or cpx62b by their admission's free cores) build that exact landed commit with `north runtime build SHA` under the build host's runtime lease, takes its `north`, `verify-north` and built-from stamp, refuses them unless the stamp names that commit and the binary's hash, and journals the builder and the binary's sha256 as a `built` event in `runtime-pins.jsonl`; it builds at full parallelism here only when no build host answers or the one it chose fails, and its log line says which. The land check builds no release runtime, so there is none of its to take. It runs the core-loop probes on the promoted runtime there, plus that runtime's `verify-north` and one scratch landing on the settling host, and only when every one passes does `north runtime promote` or `north runtime settle` ship it to the other hosts, so a runtime that breaks the core loop, its verify-north or its scratch landing is rolled back on the settling host and reaches no second one. Every other host the settling host ships to runs only the pinned runtime and never follows origin/main itself. `north runtime status` prints the pinned SHA, when it was promoted, whether it walked the spine here and since when landings that change a runtime input have waited for a promotion, read from `runtime-pins.jsonl` (or the records mirror on a host that holds another host's records). When the oldest landing that changes a runtime input has waited past 5 minutes for the promotion that makes it live, the settling host pages the coordinator once for that waiting episode, naming the landing and its wait and journaling the page, so a promotion stuck behind a build or a held update lock is noticed before settle fails the landing at its deadline. After a north landing safe-push runs `north runtime follow`, and each host's `north-runtime-follow` timer runs `north runtime update`, which pulls or builds the runtime (a build in progress always finishes), has the incoming runtime run `north check calls` against every north call on the host (system and user unit Exec lines and the store scripts they run, Claude settings hooks, and its own ssh hops to other hosts) and holds it for an hour with the live runtime kept and one proxy alarm naming the unit and line when its dispatcher lacks a verb or its table drops a subcommand the live table listed (north#825), swaps `current` (only the link moves, so a running session host keeps the runtime it started on), and swaps back with an alert to the proxy when `north runtime health` fails; for 10 min after a swap each host's tick rolls the runtime back with a proxy alarm when launch refusals (the threads ledger), session-host exits (a host that stayed stopped for a minute, never a restart onto the new runtime nor a `vn-*` scratch host) or land refusals (this host's lifecycle ledger) ran faster since the swap than over the hour before, at least twice each; a failing `agents sync` keeps the runtime, alerts once per cause and retries each tick (north#731). On the host that settles the fleet, `north runtime settle` runs the bounded core-loop probes on the promoted runtime here first, plus its `verify-north` and one scratch landing, and ships it to the other hosts in parallel only when every one passed, then runs the probes on every host per promoted SHA, on the host itself (a sandboxed worker shell reaching the hub host, the hub fetching a repository with its credential, each repository's lander minting its push token by the credential path its running `land serve` was started with, a host with no running lander or a repository no running lander serves reported once as not applicable, and a host that cannot mint by any path paged once as a host fault with no rollback, one `--test` worker per provider the host can launch answering its first turn inside a scratch state root that carries the threads ledger `north fleet` opens and widens (north#1027), with a provider whose binary or launch key is missing reported once as not applicable rather than probed, on every host but the placement-only hub, where a launch that never reaches a worker is unrun), rolling a host back with a proxy alarm naming the failing probe and quarantining that SHA there until a newer landing (north#1022); a probe the judged runtime cannot run is unrun rather than failed; a failing runtime rolls back only when it does worse than its rollback target, the newest replaced runtime whose canary passed or was kept: it fails a probe the target passed, or stops at an earlier verify-north step, and a target with no walk on record is walked on those probes first; a runtime whose target fails the same probes no later, or cannot be walked, stays live as `kept`, unshipped, with the failure recorded against both and one keyed page to the proxy per host and failing step (north#1103); a rollback never marks its target trusted, and a rollback behind a held update lock defers to the promotion holding it. Each landing that changes a runtime input, promotion, walk and rollback is journaled to `runtime-pins.jsonl`, from which the scoreboard reads three bars: promotions that broke the core loop on a second host (at most 0), the slowest rollback after its swap (at most 2 min) and landing to live p90, from each such landing to the first promotion after it (at most 2 min). Deploy and settle move a host forward only (north#651). A host set `publishes_host_facts = false` has its config facts published by the settling host (north#653). See `north runtime --help`.
