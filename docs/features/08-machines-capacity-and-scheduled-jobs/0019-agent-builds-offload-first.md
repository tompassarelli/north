- Agent builds offload first: a heavy build started inside a fleet session (`NORTH_FLEET_SCOPE` set) is offered to the `[hosts.NAME]` build hosts before the laptop decides on it, and runs on the first with room even when the laptop would admit it; it stays for local admission only when no host has room or none is configured, then waits there while the laptop is at its CPU pressure mark. Builds outside a fleet session, landing checks and pinned work (GPU, native, Warcraft, private assets) keep their classes. `heavy-command-guard` finds `cargo`, `tsc` and `bun` runs behind `bwrap`, `systemd-run`, `sudo`, `taskset`, `xargs` and similar launchers, so those route through admission too (north#259, 2026-11-06). An offload runs the whole command on the build host, so the guard refuses to route a build whose command also writes files or the git index (`sed -i`, `git add`, `cargo fmt`, a `>` redirect to a file and similar) and asks for that part as its own command first (north#674, 2026-11-06). A fleet session's Rust compile (`cargo`, `rustc FILE.rs`, `cargo-nextest`) is found through every wrapper it sits in (depbox, `nix develop -c`, `bash -c`), and on a host that does not lease its own builds it runs on a build host or is refused with the hosts' reasons, never compiled locally: the hook routes a direct `rustc` or `cargo-nextest` in a dev shell without north's shims, depbox sends `depbox run -- CMD` to a build host as CMD (the slot already runs it in the lane's dev shell), and a compile inside a sandbox that reached no build host is refused naming that, since depbox now carries the session. Each Cargo.lock the offloaded run changed is written back into the lane (north#671).
