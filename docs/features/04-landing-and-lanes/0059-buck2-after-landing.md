- Buck2 after a landing (north#1115): beside each after-landing run the lander starts `north land crate-tests after-landing` on the landed head, in its own offload slot on a build host the offload chooses and never on the lander's host, with `NORTH_LAND_TEST=buck2-after-landing` set on the job. It runs `buck2 test` of every crate that host lists, with no Cargo line and no host case, and its exit status alone is its verdict: 0 green, 1 red, 75 none (a host with no list or no store generation, or a record it cannot read). It records one row per head (head, host, exit, seconds, crates passed) in `check-timings/buck2-after-landing.tsv` and the crates it passed, one per line, in `check-timings/buck2-after-landing/HEAD.crates`. A red (exit 1) counts only when the job's log names a failing case (a nextest `FAIL` line); a red without one is no verdict (75). A red reverts the landing at once through the lander's revert only when the lander's host sets `buck2_red_reverts = true` in its `[hosts.NAME]` table of south's `agents/orchestration.toml` (absent means off), and only when the run covers one landed lane (a run across several landings names no culprit, so the Cargo run decides) and the Buck2 verdict of the landing's base is green (a base already red means the lane is not the first red). A green never reverts. The Buck2 verdicts are read from the shared action store, so a poisoned result there could cost a good landing a revert; it cannot land bad code. The Cargo run after the landing still decides its own revert, and does not queue a second one for a lane a Buck2 red already reverted. The job runs under its own offload owner (`OWNER-buck2-after-landing`), so it never shares the lander's slots with that Cargo run, and admission never gives it a slot from the lander reserve. A lander restart while it runs leaves the job on the build host to its 1800 s timeout, and that head gets no row. When the Cargo run after the same landing is red on a case of a crate Buck2 passed there, whichever of the two ends last writes `check-timings/buck2-after-landing/HEAD.trip` (crate and case, one pair a line) and tells the proxy, naming head, crate and case; the Cargo cases it failed are kept in `HEAD.red`, and the trip turns nothing off. Each Buck2 run keeps its own log (`buck2-after-landing-HEAD12-STARTSECONDS.log` in the queue logs, never truncating an earlier run of the same head), and a red run writes the failing cases (crate and case, one pair a line) to `check-timings/buck2-after-landing/HEAD.failed`, which a later run of the head only appends to. When the Buck2 and Cargo verdicts of a head disagree (Buck2 red where Cargo passes, or Buck2 green where Cargo reds), whichever ends last appends the head and both verdicts to `check-timings/buck2-after-landing-disagreements.tsv`, once per head (marker `HEAD.disagree`), and tells the proxy; the verdicts are kept in `HEAD.buck2` and `HEAD.cargo`. Neither file is written while the setting is off. A flaky Cargo case can trip falsely; that is bounded to one record and one proxy message per landed head, since the trip file is created only once. `buck2_after_landing = "off"` in `harness/defaults.toml` starts nothing. The setting is off since 2026-11-14: with `buck2_after_run` on gex45, cpx62 and cpx62b the run after a landing itself tests the listed crates through Buck2 there, so this second run repeated it, and its disagreement record compared a tests-only run with a check that also carries scans and gates (it recorded two disagreements that day, ee2e085d5f and 386d8f90bd, both a red scan or gate line and no trip).
