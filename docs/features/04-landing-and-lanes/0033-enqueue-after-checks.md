- Enqueue runs the cheap after-landing checks: a `land.after` line in `.safe-push` whose paths list carries `@enqueue` also runs in `north land enqueue` beside clippy, before the ticket is written while `landing_refusals` is `enforce` (in `shadow` only clippy runs there), so a lane that fails one is refused in the worker's turn instead of after the lander's queue wait. The checks are citations, the features and rationale indexes, the verbs sort, the owners check, code-health layers and the tests/it module list; they run on the lane's tree, and the lander still runs the same line after landing. `--no-build` is dropped for the early run so a checker the live runtime does not cover is built from the lane's tree, and checks that need the merged candidate stay after-landing only (north#697). Before them, enqueue folds the mechanical facts into the lane: it regenerates each `regenerate` index of `harness/merge-sets.toml` whose sources the lane changed and sorts each `sorted` block (the verbs table), amending the lane's last commit, so a stale index or an out-of-order verb never refuses a lane (north#729). A `land.check` line marked `@enqueue` runs at enqueue in either mode: the policy check `agent-config-check tree-policy` refuses a lane that edits harness text past a skill's byte cap with the overage in the worker's turn, where it used to refuse only at the lander (north#729). The other `land.check` scans that judge only the lane's own diff and build nothing are marked `@enqueue` too: code-health layers, experiments, citations, the features and rationale indexes, gate-shadow, the verbs sort, the tests/it module list, the nix lock, nix-entry, safe-push-verbs and run-time-data. A lane failing one is refused before its ticket is written, not in every probe of a round. On 2026-11-08 n882-context failed layers and experiments in about 10 probes; replayed at its head, the two refuse in 4.3 s and 0.02 s (north#842).
