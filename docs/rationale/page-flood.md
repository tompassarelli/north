# Page floods: bound the rate where every page passes, not in each sender

On 2026-11-10 one lander condition reached the coordinator several hundred times in 15 minutes, because the only thing deciding "already paged" was a per-sender mark and the one that failed had no ceiling below it (north#1048).

## What failed

The lander's build-lag alarm kept "already paged" in one file holding one build id. Two lander builds ran at once, each report overwrote the other's entry, and twelve lander processes, one per repository, all reported north's lag on every round. Twenty other call sites messaged the coordinator the same way, each with its own once-logic or none, and the fleet store passed every service message through.

## The method

- **Bound the rate at the choke point.** Every service message to the coordinator goes through the fleet store's send path, so that is where "once" lives: a service names a condition key, the store delivers one message per key per episode and holds the repeats for the digest. A sender with a wrong key or no key is still folded past 3 messages in 10 minutes into one line with the count, recorded as a `page-flood` incident. One test at the store covers every present and future sender.
- **One mechanism, not one per sender.** The senders' own once-marks were deleted in the same change. Two mechanisms for one guarantee drift apart, and the weaker one decides.
- **Key a "once" record by the condition, never by the last value.** A single slot holding the latest value is only a once-record while every writer holds the same value; the test with one writer cannot see that.
- **Only the owner of a condition reports it.** A fleet of identical processes each reporting a shared condition multiplies one fact by the fleet's size.
- **Alarm on incidents, not standing states.** An alarm whose condition is true most of the time trains its reader to ignore it. Measure in time behind, and let the component that owns the remedy (here the lander doctor's link-behind bound) own the condition.
- **When a rate changes, ask what was sized for the old rate.** Promotion went from every 4 hours to every few minutes; the lag limit, the mark and "restart when idle" were all sized for rare promotions.
- **Make the remedy safe to repeat.** The restart that ended the flood left a half-removed scratch worktree and broke after-landing verification, because creating it was not idempotent.
- **One cause is one message.** Rows that differ only in the unit, repository or path they name are one condition seen from many units, so the send path folds them into one follow-up with the shared text, the count and every name, and a copy re-addressed from an absent lead joins it (north#1227). The first goes out at once, because an alarm must not wait for a batch that may never come.
- **Count against the author, not the relay.** A backstop that keys on the sending process folds distinct workers' reports relayed by one service into one line, withholding exactly what the coordinator exists to read. The fold counts a relayed report against the session that wrote it.
- **Read the emitting code before staffing a fix.** Diagnosing from the symptom (twelve senders) produced a remedy that would not have worked; the 30-line function showed the cause in a minute.

## Considered and not chosen

Fixing only the lander's mark would have taken about 20 minutes and left every other sender, and the coordinator, open to the next bug of the same shape.

- Page-flood backstop (north#1048): the fleet store's send path, which every service message passes, bounds what reaches the proxy. A service names a standing condition with `north fleet send --from service:UNIT --key CONDITION`, and the store delivers one message per key per episode, holding the repeats for `north fleet held [--since DURATION]`, which prints the held log alone in well under a second; an episode ends at `--cleared`, at a new text key under the same condition (its first sentence with numbers and commit-shaped tokens blanked), or after 30 minutes in which the sender did not send it. An alarm service that names no key is keyed by its cause the same way. Whatever its keys, a service past 3 messages to the proxy in 10 minutes is folded into one line carrying the count, which goes out in place of the 4th; the rest of the window waits in `north fleet held --since 10m`, which the fold line names, and `north fleet send` records the flood as a `page-flood` incident (`north ledger incident report`). Messages from sessions, from the operator and gate messages pass unchanged, and a worker report the fleet relays under its `[from NAME · …]` header counts against that session, not against `service:north-fleet`, so four workers reporting within 10 minutes all reach the proxy while one session repeating itself still folds (on 2026-11-10 at 7:48 PM the relay folded four distinct workers' reports). The lander's link hold, dispatch's launch failure causes and north-health's failed starts send under keys, and the lander's build-lag page is gone, since the lander doctor's link-behind bound owns a lagging lander, so the senders' own once-marks (`lander-build-alarmed`, the hold file's `alarmed` word, `failure-pages.json`, the per-cause windows in `unit-failures.json`) are gone. On 2026-11-10 one lander condition reached the proxy several hundred times in 15 minutes because nothing below the senders bounded the rate. Service messages to one recipient that read the same once the unit (`*.service`), `owner/repo` or path they name is taken out (north#1227) are one group: the first goes out at once, and the rest of the 10-minute window gather into one follow-up, handed in by the fleet tick, that carries the shared text with `*` for each name, `x N` and every name (`(xK)` after one that came K times), replacing the earlier follow-up while it still waits; they do not count against the ceiling, nothing is held, and a copy re-addressed from an absent lead joins the group of the recipient it reaches. On 2026-11-12 six lander units each raised one alarm to the proxy and one copy for the absent lead, twelve messages for one cause.
