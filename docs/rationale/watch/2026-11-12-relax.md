# Relax from its own source (2026-11-12)

Record for [Relax](../../references.md#relax), a just-in-time Rust runner from the Makepad project. It answers
deep dive a of north#1247: what Relax is, read from its source and not from its landing page. The owner's thesis
under test is that North could keep to a restricted Rust so most of it runs from source, take the faster edit
loop, and pay for optimised native builds only where they are worth it. The trial with numbers and the census of
North's crates are separate boxes of the same issue, recorded in compile-reuse.md; the staged plan is its own
section below. Nothing here adopts anything.

Every claim names a file and line. A bare path is in `makepad/relax` at the pin below; a path that starts
`makepad:` is in `makepad/makepad` at its pin. Nothing was built or run: this is a reading, and a section
below lists what only a measurement can settle.

## 1. Native code

- A build script runs. Relax compiles it and its build-dependencies itself and runs it as a child process
  with cargo's environment, reading its `cargo:` lines as cargo does, with no rustc
  (`libs/relax/front/src/unitgraph.rs:6-8`, `:402-406`). Makepad's own rule is that scripts are to be removed
  from the source; until then each one still runs and is listed (`unitgraph.rs:407-423`, `:447`).
- A script counts as native when its manifest has `links =`, when it build-depends on `cc`, `cmake`,
  `pkg_config`, `bindgen`, `vcpkg` or `nasm_rs`, or when its text contains `DEP_`
  (`libs/relax/front/src/native.rs:82-107`).
- C code needs a flag and a full native toolchain. Without `--allow-c` (or `MAKEPAD_RUN_ALLOW_C=1`) a script
  that compiles C is an error naming the flag (`unitgraph.rs:486-488`; `libs/relax/session/src/options.rs:133-136`),
  and so is a script that links a static library (`unitgraph.rs:698-700`). With it, real cargo builds those
  packages and their build-dependency closure with real rustc and the system C compiler, and the archives are
  linked by the system linker into one shared library that is loaded before the program starts
  (`native.rs:1-16`). SQLite is the source's own example: `sqlite3.c` takes 28 s at `-O3` and 3 s at `-O0`, so
  the first build is unoptimised and cargo rebuilds it optimised on a background thread (`native.rs:30-37`).
  The result is cached under the run directory's `native/<key>/`, keyed by cargo flags, resolved packages, the
  C compiler and the target (`native.rs:18-20`).
- `relax check` does not run a C-compiling script without the flag; it checks that crate without the script's
  cfgs and says so (`unitgraph.rs:481-485`), and it ignores a static library line (`unitgraph.rs:695-697`). A
  check can therefore pass on a crate that a run refuses.
- A dynamic system library needs no flag: a plain `rustc-link-lib` is recorded and loaded with `dlopen`
  (`unitgraph.rs:701-704`; `libs/relax/compiler/src/os/proc.rs:6-7`).
- `extern "C"` works: a foreign symbol resolves to a `global_asm!` label, a symbol the loader provides, then
  any loaded image (`libs/relax/compiler/src/jit.rs:7125-7149`).
- Inline assembly is assembled by Relax's own assembler for x86-64 and AArch64 unless `--no-asm` is given
  (`options.rs:129-132`; `libs/relax/compiler/src/global_asm.rs:1-9`; `README.md:24`).
- `#[relax_api]` is not a way to keep a crate native under the `relax` binary. It marks the interface of a
  "provided crate", one that rustc builds into the binary that runs Relax, as Makepad's `makepad` loader does
  (`libs/relax_api/src/lib.rs:1-2`; `libs/relax/compiler/src/provided.rs:1-8`). The bare `relax` runner provides
  no crates, so every crate of a program is compiled from source (`tools/run/runner/src/lib.rs:46-48`, `:78-80`).
- What a crate that must stay native costs: a custom host binary built with rustc that links the crate with
  its `host-shims` feature (`relax_api/src/lib.rs:21-24`); every marked operation must be C-shaped and crosses
  through one uniform C call (`provided.rs:5-13`); data crosses only as marked plain types or opaque handles,
  and an operation never returns a `Vec` or `String` (`relax_api/src/lib.rs:9-15`, `:132-137`); the crate's
  source must equal what the host was built from, else the host must be rebuilt (`provided.rs:19-22`).

## 2. Procedural macros and derives

- No fixed list: any proc-macro crate of the graph is compiled by Relax itself, in process, into a separate
  "macro world" with its own std and JIT unit, each macro function compiled at its first call
  (`libs/relax/compiler/src/pmhost.rs:1-9`). Only Makepad's own derives are linked natively into the runner,
  and only while their source matches (`libs/relax/native_macros/README.md:13-16`).
- Cached where: the macro world's machine code goes to the same disk cache as program code, so rebuilding the
  world compiles nothing (`pmhost.rs:165-167`), and each parsed and expanded file is stored as a front image
  that warm runs map instead of parsing again (`libs/relax/compiler/src/front.rs:1-6`).
- Trust: the bare `relax` runner runs every proc macro with `unsafe` and full std, as cargo does; only the
  `makepad` binary sandboxes third-party macros (`pmhost.rs:11-19`; `tools/run/runner/src/lib.rs:80`).
- The name-collision gap: derive and function-like macros are registered by bare name across the whole crate
  graph and the first registered wins silently, so a derive written with its full path can expand another
  crate's macro. The file names two real collisions: `Error` (thiserror and derive_more) and `stable`
  (`libs/relax/KNOWN_GAPS.md:10-29`). Attribute macros are already resolved through the invoking crate's
  dependencies (`KNOWN_GAPS.md:26-27`).
- Two open reports touch the same area: a proc macro's dependency is compiled with the program's features
  because cargo's host and target units are merged (issue 53), and one proc-macro graph fails with E0034
  (issue 49).

## 3. The operating system surface

- Relax does not compile the Rust project's std. It compiles its own implementation of `core`, `alloc` and
  `std` (`README.md:110`; `libs/relax/compiler/std/std/lib.rs:1-3`), which mirrors the real library's module
  layout (`libs/relax/compiler/std/gen_stability.py:5-7`) and is read from the checkout the runner was built
  in (`README.md:81-82`).
- Two crates are replaced, not compiled: a graph that lists `smallvec` 1.x or `arrayvec` 0.7 gets Relax's own
  port under the same name, with features ignored (`libs/relax/compiler/std/substitutes.txt:1-7`).
- Threads are real OS threads that run on stacks Relax makes (`libs/relax/compiler/src/program_os.rs:4-9`).
- Child processes: `Command` forks and execs, with the child's code compiled before the fork; a child that
  reaches unbuilt code is ended at once. The comment records two hangs this replaced, one of 26 minutes
  (`libs/relax/compiler/src/forkexec.rs:1-22`). `pre_exec`, `process_group`, `exec` and `arg0` exist
  (`libs/relax/compiler/std/std/os/unix/process.rs:12-29`).
- Signals: the program's handlers are kept in Relax's table and run through a trampoline; a signal that
  arrives while that thread is inside a compile is delivered when the compile ends, and one that lands on a
  compiler thread is handed to a program thread (`libs/relax/compiler/src/os/progsig.rs:1-16`, `:24-31`). A
  signal with no program handler, such as a default SIGTERM, is untouched (`progsig.rs:18-20`).
- Sockets and file locks: TCP, UDP and Unix stream, listener and datagram sockets exist
  (`libs/relax/compiler/std/std/os/unix/net.rs:107-115`, `:264`), and `File::lock` and its variants are
  `flock` (`libs/relax/compiler/std/std/fs_unix.rs:371-399`).
- Raw system calls: libc's `syscall` is wrapped and passed straight through
  (`libs/relax/compiler/src/domain_res.rs:453-460`). Landlock, seccomp, rustix, nix and tokio are named
  nowhere in the repository and no test input uses them, so source cannot say whether they run.
- Environment: a program sees cargo's run-time variables (`CARGO_MANIFEST_DIR`, `CARGO_PKG_*`, `OUT_DIR`) as
  under `cargo run` (`libs/relax/compiler/src/run.rs:612-628`), and the runner sets `MAKEPAD_RUN_AHEAD` for
  every process it starts (`tools/run/runner/src/lib.rs:93-96`).
- `std::env::current_exe` reads `/proc/self/exe` (`libs/relax/compiler/std/std/sys/linux.rs:404-405`), which
  under Relax is the runner, not the program. A program that starts itself again through it starts `relax`.
- Exit codes: the program's own code is passed on, and Relax adds 86 for a JIT error, 87 for a test filter
  that matched nothing and 88 for a test target that did not load (`libs/remote/src/hot.rs:160-170`). A
  compile error reached at run time ends the process (`libs/relax/compiler/src/jit.rs:3862-3865`).
- Differences from the shipped std found by reading, at this pin: `CommandExt` has no `uid`, `gid` or `groups`
  (`std/os/unix/process.rs:12-29`); `ExitStatusExt` has no `stopped_signal` or `continued`
  (`std/os/unix/process.rs:52-57`); `std::os::unix::fs` has no `chown`, `fchown`, `lchown` or `chroot`
  (`libs/relax/compiler/std/std/os/unix/fs.rs:7-162` lists what it has); there is no `PidFd`. Missing std items
  are also the largest class of closed reports (issues 2, 28, 35, 40) and of open ones on AArch64 (issue 42).

## 4. The test runner

- `relax test <package>` runs what `cargo test -p <package>` runs, minus doc tests: the library's unit tests
  as one program, then each binary's unit tests and each file under `tests/`, every target in a process of
  its own, one after the other (`libs/relax/compiler/src/test_pkg.rs:1-9`, `:243`). A `harness = false`
  target runs as a plain program whose exit status is its verdict (`test_pkg.rs:11-12`).
- Doc tests are not run. They are counted and the count is printed (`test_pkg.rs:271-279`).
- The harness is Relax's own port of libtest, running inside the program. It takes libtest's filters,
  `--exact`, `--skip`, `--ignored`, `--test-threads` and `--list`; it has no output capture and no `--format`
  (`libs/relax/compiler/std/std/relax/test.rs:1-6`). North's suites run under cargo-nextest, which lists tests
  through libtest's `--format`, so nextest cannot drive this harness as it stands.
- `--live` keeps exactly one target warm, by default the library (`test_pkg.rs:13`, `:131-165`). It records
  which functions each test entered, inlined ones included, and after an edit of function bodies reruns only
  the tests that entered a changed function (`libs/relax/compiler/src/harness_reach.rs:1`;
  `tools/run/runner/src/help.rs:344`). It reruns every test after an edit that is not a body edit, when a
  changed function was entered outside any test's capture, or when no test reached it; a test that started a
  process always reruns (`libs/relax/compiler/src/harness.rs:246-262`). An edit that cannot be loaded restarts
  the test process (`help.rs:347`). Issue 33, open, reports that `--live` ignores edits in a larger workspace.
- A test that runs the package's own binary gets `CARGO_BIN_EXE_<name>` pointing at a generated shell script
  that starts `relax run --no-live <package> --bin <name>` (`libs/relax/front/src/unitgraph.rs:300-342`). So
  each such spawn is another JIT process that loads the cache, not a native exec, and a test that looks for
  the binary under `target/debug` finds nothing.

## 5. Checking

- Before `main`, the program's own crates are type-checked whole (`README.md:214`;
  `libs/relax/compiler/src/typeck_bg.rs:11-12`). A function's body is type-checked before it is built, so
  unchecked code never runs (`typeck_bg.rs:9`). Dependency crates are type-checked on demand, and a background
  thread checks the rest after the program starts; a type error in a dependency body that is never called is
  reported late, as a compile error of code that has not run (`typeck_bg.rs:1-9`).
- The borrow check is not on the path to running. By default a function's first code is installed and run,
  and its borrow check is queued in the background (`libs/relax/compiler/src/jit.rs:8203-8206`). A body with
  no clean verdict yet runs as code built to stay correct under aliasing (`jit.rs:8277-8284`). The source
  gives no bound on how long a verdict can take; the queue ranks an edit ahead of everything else
  (`jit.rs:8204-8206`).
- In a run, only the application's own crates are borrow-checked; dependencies are not
  (`libs/relax/types/src/borrowck/event.rs:74`, `:142-148`).
- `--check-first` borrow-checks each function before its first code is installed and refuses a rejected body,
  which then ends the run when called (`jit.rs:3868-3871`, `:8053-8063`). The source states no cost for it
  beyond "the default never waits" (`tools/run/runner/src/help.rs:225`).
- `relax check` type- and borrow-checks every function of the package's workspace crates and compiles nothing
  (`libs/relax/compiler/src/check.rs:1-4`). Its cost, by the README: on a large package a cold check takes
  longer and more memory than `cargo check`, and an edit can re-check more than it needs to
  (`README.md:36-38`). Clean per-crate verdicts are stored and replayed (`libs/relax/compiler/src/check_reuse.rs:42-48`).
- Is a passed `relax check` as strict as rustc's? That is the stated aim: "rustc is always right", and a
  disagreement is fixed by porting rustc's rule (`libs/relax/CONTRIBUTING.md:37-38`). Strict Rust is the
  default and the relaxations are opt-in per crate (`libs/relax/base/src/relaxed.rs:5-9`). The differences it
  admits or that reading finds:
  - it accepts `#![feature(..)]` on any build, where stable rustc reports E0554
    (`libs/relax/types/src/feature_gate.rs:117-119`), and it does not judge feature gates on tokens a macro
    wrote (`feature_gate.rs:9-11`);
  - a crate whose C-compiling build script was skipped is checked without that script's cfgs
    (`unitgraph.rs:481-485`);
  - the bare-name macro gap can expand the wrong derive without an error (`KNOWN_GAPS.md:20-22`);
  - two lint differences remain (`KNOWN_GAPS.md:46-78`);
  - it has rejected valid programs: false E0277 and E0283 (issues 10 and 32, closed) and one not yet
    reproduced (`KNOWN_GAPS.md:31-38`);
  - it has passed a failing one: `relax check` exited 0 after printing errors from dependency crates, reported
    as "CI cannot gate on it" (issue 39, closed the day it was filed).
- It is not clippy, and there is no CI on the repository; maintainers run their own gates
  (`CONTRIBUTING.md:94-96`).

## 6. Live patching

- Patched: function bodies, constant values (their readers are recompiled), initialisers of statics that
  have not been placed yet, and some layout, macro and visibility edits; a renamed field applies, and a type
  with no live value takes its new layout (`libs/relax/compiler/src/reload.rs:7-13`). An edit of several files
  is one all-or-nothing transaction: everything is type-checked, borrow-checked and compiled before anything
  is installed (`reload.rs:3-6`, `:16-23`).
- Not patched, each with its stated reason: a changed struct, union or enum layout while values are live, a
  type alias, an import, a trait's items or bounds, an impl header or item list, an extern block, a
  `macro_rules!` definition and an item macro (`reload.rs:932-945`). The README adds that Relax then offers a
  restart (`README.md:41-42`). Changes to the Cargo graph, build scripts, std or the runner itself are not
  taken in place either (`libs/relax/compiler/src/reload_host.rs:1-3`).
- What a long-lived service would see: the next call of a patched function runs the new code while frames
  already on a stack finish the old code, which is never freed (`README.md:216-221`). A loop that never
  returns keeps its old body, and the landing check offers a restart when old code remains on a stack
  (`reload.rs:13`). An initialised static keeps its value (`reload.rs:8-9`). Machine code only grows, so
  memory grows with every patch (`README.md:33-34`). After an unsupported edit the process keeps running the
  old code until it is relaunched (`reload.rs:11-12`).
- A panic parks its thread with the stack intact, up to 10 minutes at a terminal and 2 s when nothing is
  attached (`README.md:56`); `--unattended` never parks and ends the run on a compile error
  (`tools/run/runner/src/help.rs:228`). Two closed reports are a 600 s wait at a panic with nobody attached
  (issue 3) and a run that parked forever when not interactive (issue 21).
- Every run listens on a local socket for `relax inspect` (`help.rs:409`) and watches the sources with inotify
  (`libs/relax/compiler/src/reload_watch.rs:1-5`).

## 7. Start-up, memory and the code cache

- Where: `<cargo target dir>/makepad-run`, so per workspace and per target directory
  (`libs/relax/compiler/src/cache.rs:20-22`; `libs/relax/CONTRIBUTING.md:69-71`). One store file per crate
  version, shared by every program that uses that crate (`libs/relax/compiler/src/store.rs:1-3`). Each new
  package starts cold (`README.md:86-87`), and so does each git worktree: pull request 57, open, adds sharing
  between worktrees of one repository.
- What it holds: machine code per function with relocations expressed as stable identities, borrow-check
  verdicts, and front images of parsed files (`cache.rs:1-6`, `:15-19`). A start-up image lets a later run
  install the code of everything its start used before `main`, in one pass
  (`libs/relax/compiler/src/cache/image.rs:1-10`).
- What invalidates an entry: its key is a content hash of the Relax build, the codegen configuration, the
  function instance, the interface fingerprints of every crate it can depend on, and its own body and
  position; never a timestamp (`cache.rs:6-14`). An edit of one body recompiles that function and the code
  that inlined it (`cache.rs:15-17`). A rebuild of Relax that changes anything that generates code, including
  the rustc that built it and its CPU features, starts from no stored code
  (`libs/relax/compiler/src/codegen_id.rs:1-12`; `reload_host.rs:18-20`).
- Size: 120 to 190 MB for a hello-world package (`README.md:35`). The cap is `MAKEPAD_RUN_CACHE_MAX`, by
  default twice what the run uses and at least 4096 MB, pruned least recently used (`cache.rs:22-24`,
  `:4688-4695`). Native build outputs are outside the cap: issue 46, open, reports 9.8 GB of a 12 GB run
  directory.
- Concurrency: readers take a shared lock and map the file, a writer appends and flips the header, and a
  crash leaves the previous index valid (`store.rs:13-17`).
- Start-up numbers, all the README's and none measured here: hello's first run 0.24 s on a 16-core x86-64
  Linux box and later runs 0.01 to 0.07 s (`README.md:84-86`); a large game 11 s cold and 1.15 s warm on an
  M4 MacBook (`README.md:15-16`). Building the runner took 53 s on that Linux box (`README.md:84`).
- Memory: the compiler, its caches and every published code version share the program's process
  (`README.md:33-34`). The README gives no figure.
- Speed once warm: 1.14 to 1.26 times a native release build's time on the workloads profiled most, 2.3
  times on dense numeric loops, measured against `--release` with `target-cpu=native`; a broader run of 18
  workloads came out slower and is being re-measured (`README.md:157-176`).

## 9. Makepad's agent workflow

- The pieces: one master process holds the queue, the landing train and the post-landing checks, and each
  build box runs a hub that keeps one JIT build and one code cache for every lane on that box
  (`makepad:docs/agents/dev-workflow.md:30-34`, `:171-173`). About four in five cache lookups hit
  (`dev-workflow.md:172-173`). After each landing every box prebuilds the JIT and warms the caches, and a
  lease preempts that (`dev-workflow.md:47-48`; `makepad:libs/devhub/src/sync/prewarm.rs:1-14`).
- The loop: a live session ships each saved file to a box, where the JIT patches the running app or the warm
  test process and answers with a one-line verdict (`dev-workflow.md:8-10`). One day of all lanes, median and
  p90: 0.1 and 0.4 s to ship, 3.6 and 86 s to patch, 15 and 138 s from save to verdict; one JIT run as a job
  112 and 489 s, queue included (`dev-workflow.md:16-20`). The devhub library's own tests take about 40 s as
  a JIT run against about 2.3 minutes native (`dev-workflow.md:276-277`).
- Native builds are refused for lanes, except for the JIT's own crates, a package with an open JIT miss, a
  platform with no JIT, a test that measured routing sends to cargo because the JIT was slower end to end, and
  an explicit `--native` with a reason (`makepad:libs/devhub/src/lease/native.rs:1-9`; `makepad:AGENTS.md:119-127`).
- What is checked before a merge: nothing, by the train. "Land = merge only. Nothing builds or tests before
  the merge"; the checks run afterwards in buckets and none blocks the train (`dev-workflow.md:186-187`;
  `makepad:libs/devhub/src/land.rs:8`). The lane's own pre-land check is one JIT test run by convention
  (`dev-workflow.md:158`). Relax's README says each change is "checked under Relax before it merges"
  (`README.md:152-153`); Makepad's own workflow document says the train does not check. Reds are fixed forward
  (`dev-workflow.md:202`), and the tests bucket reports 23 to 48 minutes after a landing (`dev-workflow.md:25`).
- By which compiler: the post-landing shards run under the JIT (`makepad check`, `makepad test`,
  `makepad run`) "except where it cannot be yet" (`makepad:libs/devhub/src/orch/ci.rs:10-20`).
- What they still build with rustc: the runner and devhub themselves, rebuilt on every landing and rolled to
  every hub a median 5.8 minutes later (`dev-workflow.md:41-46`), with a clean build of the JIT taking 68 to
  71 s on a 16-CPU box (`makepad:.cargo/config.toml:8-10`); every lane whose edits touch crates linked into the
  JIT gets a JIT of its own (`makepad:libs/devhub/src/lease/loaders.rs:20-23`); the cross targets the JIT does
  not build, checked with `cargo check --release --target` (`orch/ci.rs:16-17`); a rotating third of test
  binaries natively on Windows (`orch/ci.rs:15`); and whatever ships (`README.md:45`).
- The count of nine lanes and 300 jobs an hour is the README's (`README.md:152-153`); the workflow document
  gives no lane count. Its own list of what is still slow: agent wait 53 s median and 6.0 minutes p90, with
  waiting for cores the top blocker; cold patches 86 s p90; hubs run a landing 6 minutes after it
  (`dev-workflow.md:291-298`).

## What reading says about the thesis

- For: the pieces the thesis needs exist in source, not only on the page. Build scripts and proc macros run
  without rustc, the cache is keyed by content and shared per crate, and a warm test loop that reruns only the
  tests an edit reached is implemented.
- Against, for North as it is: a crate that links SQLite needs cargo, rustc, a C compiler and a linker anyway;
  the test harness is not libtest, so nextest does not drive it; a test that runs North's own binary starts a
  JIT per spawn; `current_exe` names the runner; the std is a rewrite with gaps in exactly the process and
  ownership calls a harness uses; and the code is 40 days old with a correctness report that a check passed
  on errors. Makepad itself keeps the borrow check and all gating off the merge path and fixes forward, which
  North's landing does not.
- So a restricted-Rust convention would have to cover the OS surface and the test shape, not only language
  features, and the landing verdict stays on rustc at every stage. That is for the plan to decide.

## What only a measurement on North can answer

1. Of North's unit tests, how many load and give nextest's verdict under `relax test`, per crate, with the
   first error of each that does not (the trial's rule of 80%).
2. Seconds from a one-line edit to a verdict under `relax test --live` against the nextest rebuild, on a
   crate inside North's 65-crate workspace, since issue 33 reports live edits ignored in a large workspace.
3. Cold and warm start time, peak memory and cache size for a North crate, per lane worktree and with a
   shared `CARGO_TARGET_DIR`, since each worktree starts cold by default.
4. Whether North's process code runs under Relax's std: `Command` with `pre_exec` and process groups,
   `flock`, Landlock and seccomp calls, signal handlers, and self re-exec through `current_exe`.
5. How many North crates build under `--allow-c` and what that first native build costs, and whether any
   pair of derive names in North's graph collides under the bare-name rule.

## Staged plan

Deep dive c of north#1247 (2026-11-12). It turns the reading above, the census
([compile-reuse.md](../compile-reuse.md#runnable-from-source)) and the trial (compile-reuse.md, "Relax: a
just-in-time Rust runner") into stages that can each be started, measured and ended alone. The thesis is the
owner's: hold North to a Rust that runs from source, take the faster loop, and pay for native builds only
where they are worth it. The plan neither assumes it nor argues against it; each stage says what number on
North would show it true. Nothing here adopts anything.

### What the records say first

- The loop's cost (north#1115, comment of 2026-11-12: 347 landings in 24 hours, two build hosts, 1,013,000
  core-seconds). The hand-in check is 329,000 (32%): its checks 143,800, its test listing 103,100, checks sent
  to a slot 82,200, and 51,200 of the whole in runs that exited non-zero. A worker's own builds and tests are
  277,200 (27%); of the 108,000 spent in lanes, tests are 49,100, clippy with tests 19,400, plain builds 16,400
  and clippy 15,400. The runtime release build is 37,300 (4%), 49 builds.
- Where rustc is slow. One crate's own loop is already seconds: from a one-line edit to nextest's verdict
  1.92 s on north-foundation, 1.59 s on north-graph and 8.45 s on north-base, 6.7 s of that the tests running
  (the trial). The slow case is a hub edit across the workspace: one line in north-foundation, then
  `cargo test --workspace --no-run`, is 79 s, 108 core-seconds and 122 units, 65 of them test harnesses, with
  216 link-seconds (north#1115).
- What Relax did on North. 17 of 1,501 library unit tests ran. On the one crate with compared verdicts it was
  no faster, 2.11 s against 1.92 s, because the tests took 2.14 s under the JIT and 0.71 s native. No hub and
  no crate that links SQLite ran, so the slow case above is not measured.
- The ceiling. Library unit tests are 1,501 of 1,861 tests. Crates outside the native group hold 1,371 tests
  (73.8%) and 45.5% of a day's test seconds; the root's two test binaries are 49.7% of the seconds, run the
  built `north`, and stay native at every stage (the census).
- What refuses a hand-in. In the 7 days to 2026-11-12, `north land gate-stats --since 7d` counts 487 lander
  refusals, nextest 26 of them and clippy 9, and 57 checks before queueing that exited 100, the test runner's
  code for a failed test. Most refusals are scans that need no compiler.

Three things follow, and the stages are built on them.

1. The trial's first blocker is probably North's own setting, not an upstream gap. `.cargo/config.toml` sets
   `[resolver] feature-unification = "workspace"`, so the cargo that Relax starts resolves `rustix` for one
   package with the whole workspace's features, and Relax resolves for the one package as stock cargo does.
   That fits both of the trial's observations: north-tui, whose own graph has `crossterm`, passed, and a
   workspace cut to one member still failed because the root stayed a member. Inferred from the two sources and
   not run. One run settles it: the trial's command with `CARGO_RESOLVER_FEATURE_UNIFICATION=selected`.
2. The SQLite boundary does not decide this. If `--allow-c` works once blocker 1 is gone, every crate outside
   the native group is reachable with no move in North. If it does not, the leaf crate of the census reaches 387
   tests (20.8%) and 8.9% of the test seconds, and the rest waits on 408 call sites moving behind record
   crates. So the leaf is the architecture plan's call (layers 1 and 2), made on its own grounds, and no stage
   below waits for it.
3. The comparison is Buck2's loop, not today's Cargo loop. The next section says what the store gives each
   stage, so that no stage builds it a second time.

### What Buck2's store gives each stage for free

From [compile-reuse.md](../compile-reuse.md#lanes-north1115-box-6), measured 2026-11-12; boxes 5 to 9 of
north#1115 are open, so these are given at the cut-over, not today.

- To the worker's loop: a fresh lane's check build is 4.3 s once any lane has built its inputs, with no seeded
  target, and a test target that passed on the same inputs on a worker is answered from the action cache. Not
  given: incremental compilation is off, so an edit recompiles its crate and every crate above it from scratch
  (3.9 to 8.3 s for the longest first-party crates), links each reached test binary again, and reruns every
  case of each. That remainder is the only part of the loop a from-source runner could take.
- To the hand-in: the test listing without a compile (103,100 core-seconds a day), and a pass reused from the
  worker's own run of the same tree. Not given: a failure is never cached, so every red runs again.
- To a promotion: the release build takes unchanged crates from the store (north#1115 puts 12,000 of the
  37,300 core-seconds a day there), and the cadence builds ahead of each slot, so a slot promotion does not
  wait for a build ([propagation.md](../propagation.md)). Only a `Live-fix` promotion waits: 74 s warm, 6 min
  10 s cold.

### Stage 0: a number on the case that could win

- Changes: nothing for a worker or a landing. One lane reruns the trial in its scratch clone on a build host,
  past blocker 1, with `--allow-c`.
- Bar, all three, by the trial's own rule on the population it could not reach:
  1. At least 1,201 of the 1,501 library unit tests (80%) run and give nextest's verdict test by test. Read by
     `MAKEPAD_RUN_ALLOW_C=1 CARGO_RESOLVER_FEATURE_UNIFICATION=selected relax test CRATE` over the 56 crates
     against `cargo nextest run -p CRATE`; `comm -3` of the two sorted verdict lists prints nothing.
  2. From a one-line edit to the verdict, at least five times shorter than rustc on a hub: north-base in 1.7 s
     or less against 8.45 s, and for one line in north-foundation the unit tests of its 51 dependants in a
     fifth of the time `cargo nextest run` takes over the same packages after the same edit, same host, same
     hour (the workspace test build after that edit is 79 s today; `north code-health build-time` times the
     rustc side). `--live` may
     be used, since rerunning only the tests an edit reached is the one thing rustc does not do.
  3. A fresh worktree's first verdict within 60 s, the native build of SQLite and `ring` included, with the
     cache size and peak memory recorded (lanes hold 1.7 to 10.4 GiB of Cargo target today).
- Stop rule: under 1,201 tests, or neither hub figure at five times, ends it as not worth it now, with the first
  error of each crate recorded. Two tries at one blocker, then stop. What would reopen it is named upstream
  work, not time passing.
- Stays on rustc: everything. Nothing runs from source outside the scratch clone.
- North restricts itself to: nothing. The override is an environment variable for the cargo Relax starts;
  `.cargo/config.toml` keeps workspace unification, which the landing's slots rely on.
- Upstream first: nothing; the pin is `ce52155`.
- Leaving costs: deleting the scratch clone.

### Stage 1: the worker's own test loop

- Changes for a worker: for a crate in the covered set, the command a worker runs for its unit tests answers
  from source. First in shadow, where both run and the worker sees rustc's answer; then from source alone,
  with rustc's answer at the hand-in. Each host builds Relax once per pin (169 s, 3.6 GB peak) and keeps one
  code cache for all its lanes. Changes for a landing: none.
- Bar, on one build host, over the first 500 shadowed runs (a day holds 1,718 leased lane runs):
  1. No more than one differing verdict in the first 10,000 test executions, in either direction. A green from
     source over a red costs a failed hand-in; a red from source over a green sends a worker after a fault that
     is not there. Read as in stage 0.
  2. The median edit-to-verdict is a fifth of the rustc run it shadows or less, against the build system that
     host runs then. After the cut-over that is Buck2, and box 9 of north#1115 holds its one-line-edit figure.
  3. The from-source runs use half the core-seconds of the rustc runs they shadow or less: the sum of
     `cpuSeconds` per lease in `machine-capacity-usage.jsonl`, by the per-stage query of north#1115's comment.
- Stop rule: a second differing verdict, a ratio under five, or a pin bump that takes coverage under 80% twice.
  Bumps are forced: upstream has no releases and lands hundreds of commits a week, and a new build of Relax
  starts every cache cold.
- Stays on rustc: clippy (Relax is not clippy; 15,400 core-seconds a day alone and part of 19,400); the 360
  tests that are not library unit tests; the native group (the root package, north-land-sandbox, north-runtime
  until L18 of north#1276); both doc tests; the whole hand-in, the lander, the after-landing run and the
  release build. Why: a test that starts the built binary needs the built binary, and a verdict that lets a
  change land has to come from the compiler that builds what ships.
- North restricts itself to, with the cost in today's code:
  - Conventions 2 to 5 of the census (no build script that compiles C, a closed list of macros, no
    `#![feature]`, no `unsafe`): nothing breaks them today, so the cost is three land scans beside the lint
    that already forbids `unsafe`.
  - A unit test that does not need a process of its own. Nextest gives each test one and Relax runs a target's
    tests in one process. How many tests that breaks is not known; bar 1 counts them.
  - No reliance on `current_exe` in a covered crate's unit tests (convention 8 is the wider rule: the 26
    crates that call it in non-test code would take the program's path as an argument).
  - Not required: the SQLite leaf, if `--allow-c` passed stage 0.
- Upstream first: its feature resolution agrees with cargo's or the override holds; a test harness that lists
  and reports in a format a program reads, or `--list` and `--exact` stable enough for `north-test-cases` to
  drive; one cache shared by the worktrees of a repository (pull request 57) or a shared target directory that
  works; live tests in a large workspace (issue 33) if `--live` carries bar 2; a non-zero exit on every error
  (the class of issue 39).
- Leaving costs: one route and one pin deleted. The rustc command never left, and the conventions cost
  nothing to keep.

### Stage 2: the hand-in's early answer

- Changes for a worker: `north finish` starts a from-source run of the unit tests the change reaches beside
  the check it runs today. When that run reports a red, the hand-in builds and runs that one test binary with
  rustc first and refuses on rustc's red, sooner than the full check would have. A green from source changes
  nothing. Changes for a landing: none, and what refuses a hand-in is the same failure as today.
- Bar, in shadow over the next 50 hand-ins that end red on a library unit test:
  1. In at least 40 of them the from-source red came 60 s or more before rustc's.
  2. The median time from the call to the refusal would be a fifth or less of what it was.
  3. No hand-in is refused or delayed by a from-source red that rustc does not confirm: zero, read from the
     shadow's record of each early red and the rustc verdict on the same test.
- Stop rule: fewer than 10 such hand-ins in a week (test failures are 26 of 487 lander refusals and 57 hand-in
  exits a week over all crates, so the stage may be too small to matter); bar 1 or 2 missed; or the cut-over
  to Buck2 bringing the median rustc time to a red under 60 s on its own.
- Stays on rustc: every verdict and every refusal; clippy; the mutant-kill scan; integration tests.
- North restricts itself to: what stage 1 did, and nothing more.
- Upstream first: what stage 1 needed, held over a pin bump, and exit codes that tell a failed test from a
  JIT error (86, 87 and 88 exist today).
- Leaving costs: one step of the hand-in deleted.

### Stage 3: North run from source on one canary host

- Changes for a landing: at a promotion the canary host starts North's long-lived processes with
  `relax run north --bin north` from the commit's source and runs the canary probes against them, with no
  release build first. Changes for a worker: none.
- What it can save is small and conditional. The release build is 4% of the hosts' core-seconds and a slot
  promotion already has its artifact, so the gain is a `Live-fix` reaching the canary 74 s to 6 min sooner. A
  promotion needs no release build only if every host runs from source. While other hosts run the release
  artifact, a canary that passed from source has tested another program than the one that ships, and the
  release artifact still needs its own canary pass.
- Bar:
  1. `relax run north --bin north -- --version` runs; the trial did not reach it.
  2. On 100 promoted commits in a row the from-source canary and the release artifact's canary give the same
     verdict on every probe: zero disagreements in the `ordered` and slot rows of `runtime-pins.jsonl`.
  3. The sandbox enforces the same from source: the 19 north-land-sandbox cases and the 13 `worker_sandbox`
     cases of `north::it` pass.
  4. A lander that has run 24 hours from source holds at most twice the resident memory of the release build's,
     since patched and compiled code is never freed.
  5. Landing to canary verdict under 60 s at p90, the bar north#1022 already sets.
- Stop rule: one disagreement in bar 2 ends it, because predicting the release is the canary's whole job; so
  does one failing sandbox case or memory over twice.
- Stays on rustc: the artifact every other host runs; north-land-sandbox and the worker sandbox (ptrace,
  Landlock, seccomp, mount); the brokers. Why: these enforce what a worker may reach, and Relax's sources name
  none of those interfaces, its std is a rewrite, and its check has exited 0 after printing errors (issue 39).
- North restricts itself to: kernel-interface code in named leaf crates (convention 6; L18 and four small
  moves); a program path handed in instead of `current_exe` in 26 crates, since North starts itself again and
  under Relax would start the runner (convention 8); the root's 32 `rusqlite` calls through `--allow-c`.
- Upstream first: releases and continuous integration; Landlock, seccomp, `rustix` and tokio shown to run
  under its std; an unattended mode that ends on a panic instead of parking a thread; a bound on memory under
  repeated patches.
- Leaving costs: the canary host follows the release artifact again at the next promotion.

### Where the evidence leans

Stage 0 is cheap and its answer is not known: the trial stopped before the only case where a from-source
runner has room to win, and the blocker that stopped it looks removable from North's side. Stages 1 and 2
have a narrow target once Buck2's store is live, and stage 2's is the narrowest, because test failures are
about a twentieth of the lander's refusals. Stage 3 as named cannot drop the release build without changing
what the canary means, and it puts the worker sandbox on a compiler that is 40 days old, so it should be
opened only by its own later decision, after stage 1 has held over several pin bumps. The conventions are
nearly free: North already forbids `unsafe`, has no `#![feature]`, one build script and no macro clash. The
restriction that costs code is the operating-system surface (`current_exe`, the sandbox, SQLite), and that is
the architecture plan's work whether or not Relax is used.

### Ways forward

Relax ran 1% of North's unit tests and was no faster on the one crate it ran, but the case it could win, a hub
edit that costs 79 s of rustc before the first test, was never reached, and what stopped it looks like North's
own cargo setting. Three ways to go on from here, with what each costs; this plan recommends the first.

1. Measure first. One lane runs stage 0; stages 1 to 3 open only on its bars, each as its own later
   choice. It serves the goal North ranks first, first-try success and a landing p90 under 60 s, by leaving the
   Buck2 cut-over, where the measured core-seconds are, undisturbed. Cost: one worker lane and one session on
   a build host; nothing to undo.
2. Commit to the restricted Rust now. Run stage 0 and, beside it, the groundwork: the SQLite leaf crate and a
   land scan on `rusqlite`, `ring` and `-sys` edges, land scans for conventions 2 to 5, and the program path in
   place of `current_exe`. Cost: a new crate, five north-base files, the imports of 9 crates and call sites in
   26, on files the Buck2 cut-over and the architecture boxes are also changing, paid before any number says
   Relax can use it. None of it is wasted as architecture.
3. Park it. No lane; read upstream again when it has a release and continuous integration and when box 9 of
   north#1115 has Buck2's one-line-edit figure. Cost: nothing now; the hub number stays unknown and North has
   no say in an upstream that is still forming.
