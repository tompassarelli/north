# North features

What each harness command and app feature does, grouped by job. The commands live in [bin/](../bin/);
[harness.md](harness.md) shows how they fit together. Each command's `--help`, its code and
[harness/defaults.toml](../harness/defaults.toml) are authoritative for flags, defaults and thresholds;
a number quoted below describes the behaviour when it was written.

CPU offload: [`north nexus-run`](nexus-run.md) sends an owned working tree over SSH, runs its command under Nexus capacity admission, and retrieves selected outputs. The private stock asset cache stays outside Git on Nexus.

## The `north` app

- Interactive fleet screen: `north` or `north fleet` opens the fleet list, transcript and digest.
- Work items: `north work list`, `north work search TEXT`, and `north work show REPO#N`. Search includes matching open and closed issues. Work edits use `north work claim REPO#N [--by NAME] [--eta MINUTES]`, `release REPO#N [--to NAME]`, `need REPO#N BLOCKER#N`, `unneed REPO#N BLOCKER#N`, and `close REPO#N --comment RESULT`. Changes are recorded on the GitHub issue.
- Where work state lives: GitHub holds titles, bodies, checklist, state and blockers. NorthThreads holds current holders, elapsed time and ETA, handoffs and worker runs. North reads both and writes through their commands.
- Skills and hooks: `agents status`, `stale`, `inspect ID`, `path ID`, `on ID`, `off ID` and `sync` (each also `north config agents ...`) list, toggle and publish the catalog's skills and hooks; [harness.md](harness.md#install) describes what `agents sync` publishes.

## Staffing and routing

 - Claude account profiles: `north fleet launch --provider claude --account LABEL --name NAME PROMPT` uses the account's local profile and records its label for restarts. Omitting `--account` keeps the current default. South owns account IDs, host profiles, plan selections and required plans for automatic routing. `agents sync` projects the default Claude harness files into those profiles while credentials and session history stay separate. A profile awaiting its required plan is available explicitly but is excluded from automatic routing until its OAuth tier confirms that plan.
- Interactive Claude and Codex: `claude` and `codex` are the installed vendor runtimes (`~/.local/lib/{claude,codex}/current`) on their default homes; sessions on other accounts run through `north fleet launch --provider claude|codex --account LABEL`.
- Fleet accounts: each `~/.local/state/north/profiles/claude-LABEL` with credentials is one account unless it is logged in to the same account as another label (the sha256 prefix of the `oauthAccount.accountUuid` in its `.claude.json`, over the fleet profiles and this host's `[accounts.claude] profiles`); the label `[accounts.claude] labels` declares for that login keeps it, else the first label by name. A duplicate is left out of `north fleet accounts` and the fleet TUI's launch form (named on stderr with the label it shares a login with), refused by every launch and revive (CLI or TUI, even with `--pin` or `--test`), and unavailable to placement, which also skips any pace-control account with no fleet profile.
- Account owner hosts: a label that `[accounts.claude] profiles` declares only for other hosts is foreign here (north#177): a copied `.credentials.json` shares one OAuth refresh token, so a refresh on either host revokes the other copy. A foreign label is left out of `north fleet accounts` (named on stderr with its owner hosts), refused by every launch and revive naming the owners, and unavailable to placement; placement may still put it on an owner machine, and `north fleet launch --cwd HOST:/PATH` names that machine and its directory. Pace sampling reads its usage through ssh on the owner host instead of starting `claude` here. It starts a provider's local usage adapter only on a host its `[accounts.PROVIDER]` table admits (one its `profiles` name, or any host when it declares no `profiles`), so a provider with no such table, such as Gemini, is not read. A label with no declared profile hosts runs anywhere. A launch whose first turn answers `Not logged in` restarts once, and one that answers `OAuth session expired` is refused naming the account and host; both are recorded in `fleet/.credential-failures.jsonl`.
- Routing: `agents plan` prints one difficulty band table from scalar tier starts, with account usage and project priority, share and target. `agents plan` shows each account’s used percentage, linear pace, available weekly dollars and reset timestamp, and routes each tier to the soonest-expiring under-pace account. Claude drains to 5% left at its reset. `--json` exposes the same metrics and routes; `--at FILE` replays recorded routing decisions. Project `share` is a percentage of rolling seven-day available dollars; `target` is its deadline.
- No pace hold: `north fleet launch` placement and the Agent-tool spawn gate (`north pace reserve` and the refusal it prints) refuse a new worker on an account only when its 5h window is at or over 95%, its measured 5h burn is over `five_hour_burn_cap_pct_h` (50%/h), or the provider reports its week (`week` or `LIMIT:week`) exhausted; the pace controller's held, over and allowed workers, pace lines, projections and drain grants never refuse. `agents plan` (north pace plan, crates/north-core/src/router/choose.rs) still routes by pace and drain grant at a Claude account's week drain floor (north#185). Each hold names its measured reason and when that window resets, in local 12-hour time. The spawn gate keeps its CPU and landing-flow checks and the usage-gate money refusal for an account whose overflow can bill money; it holds no calibrated reservation.
- Resident cap: `north resident-cap gate claude|codex ARG...` refuses a new resident session on a host whose `[hosts.<hostname>] resident_cap = N` in orchestration.toml is reached, counting live claude/codex CLIs listed by `north fleet list --json` plus unregistered top-level interactive ones, and print `Hold: <host> has N/N resident agent CLIs; place this worker on laptop|cloud` (exit 3). `--cloud`, `-p` and codex exec/app-server launches are not resident; `CASE=URGENT` with a FACT passes; hosts without the key are never held; `north resident-cap status` prints the live count and cap.
- Token-only usage: a Claude account this host declares a `token_file` for and holds no login of, which has no `~/.claude.json` usage cache to read, is sampled by `north pace sample` with one one-token Messages request on that token, whose `anthropic-ratelimit-unified-5h-*` and `7d-*` headers give its `session` and `weekly_all` windows. `agents usage` names an account's plan from its refreshed `.claude.json` `organizationRateLimitTier`, else its sign-in credential's tier, else `[accounts.claude] plans`.
- Usage resets: `agents usage` publishes fresh readouts through `threads ingest` to the authoritative ledger, with its existing offline spool. Remote clients read history from the mirrored snapshot and overlay fresh readouts in memory. A stale plan readout fails loudly. `agents usage` keeps each account's used percentages and reset times and appends reset availability and its source. `usage-web-read` reads the Claude usage page and account UUID inside automation Chrome, caches per-kind counts and expiry by hashed account in `~/.local/state/agents/usage/claude-web.json`, and preserves other accounts and the previous cache on failure.
- Usage read: `agents usage` and `agents usage --json` are served by `north usage`: the latest reading of each account window from the threads ledger (the mirrored snapshot on a remote client, refreshed once over ssh when it fails its integrity check), as the per-account table with its windows, billing, reset availability, burn, plan and the cost lines, or as JSON with a `stale` flag, byte for byte as harness/lib/usage.py printed them; the claude rows of accounts this host does not hold, and providers outside the model catalog, are left out. `agents usage --write-pace-gate` (the pace sampler's call) rewrites `usage-gate.json` from Rust, building the router's context in process: its money refusals, per-account refusals, window projections and pace reading equal those usage.py wrote. `agents usage --refresh [--local]` reads every `usage_*.py` and `billing_*.py` adapter beside harness/lib in parallel (30 s each) and, unless `--local`, each labelled account signed in on another machine over ssh (45 s), records the readings in the usage table (a mirrored client publishes them to the ledger host first), rewrites `usage-gate.json` under the pace-control lock, and sends one desktop notice per promotion ending within seven days. `agents usage --fast PROVIDER [--cached]` prints `on` (exit 0) or `off` (exit 1) from routing, refreshing that provider first unless cached; `agents usage --gate PROVIDER` is `north pace gate PROVIDER`.
- Worker estimates: `north worker-ledger --recommend 'FACETS'` chooses the cheapest tier meeting the 80% measured success threshold and adds the recommended tier’s eta from the sample cell, backing off Surface, Verify, Scope, then Spec until three samples are available (or Category alone): `eta active <median>m (p25 <a>–p90 <b>, n=<N>) wall p75 <W>m wait median <X>m` from the runs that recorded active minutes, or `eta wall <W>m (p75 of n=<N>, ...)` when too few did; no samples prints `eta n/a (n=0)`.
- Follows boxes: `threads queue follow REF --tier T --parent NAME` queues a brief from stdin, whose `Follows:` line names the predecessor commit subject, SHA or issue ref. `follows-release` releases a box when its predecessor reaches origin/main, then sends the assignment to its Fleet parent with `north fleet send`.
- Project quote: `agents plan --quote --project P --boxes N` reads the project target from `south:agents/orchestration.toml` and the worker ledger, prints the measured completion date and dollars, and asks one date-and-budget decision for dated projects; undated projects ask none. `agents flow` prints the needed closure rate for each project target.
- Fleet idle (north#252): a session host parks an idle session after its idle limit (`--idle-exit`, default 10 minutes), and a wake within the hour resumes on the warm prompt cache. A session at 200k context tokens or more that is not finished stays up instead, and at 55 idle minutes, before the 1-hour cache expires, the host writes a bare `/compact` frame to it (headless Claude Code runs it as the command) and parks it after its idle limit; past 60 idle minutes it parks uncompacted, since the cache is cold. A session whose last report opens Done, Not done, Split, Stop or Blocked, has a parent or a task and parents no live session exits instead of parking, by 60 idle minutes even with a background task still out; its transcript and worktree stay and `north fleet send` or `revive` brings it back. A host told to end (SIGTERM at a host restart) passes that signal to its runtime and marks such a finished session exited too, so a restart leaves it stopped instead of parked for a notice to revive. A host journals each prompt it writes to Claude until Claude echoes it into a turn (`unaccepted.jsonl` in the host directory), and a host ended with a prompt still unechoed leaves its worker parked, not exited; the worker's watchdog (any session with a parent or task) then revives it (if that watchdog outlives the restart), and `north fleet stop` discards the journal, and the new host writes the journaled prompt once more, so a message queued just before a restart runs without a new `send` or `revive`. A prompt that is not echoed on that second host is dropped. The host journals a prompt before it acknowledges the write, and `north fleet list` and `show` call a running session working while its journal holds a prompt: a revived Claude echoes a queued prompt only once it has loaded the resumed conversation, several seconds on, so until then its stream still ends on the old turn (north#245). Every Claude profile compacts on size at 500k (`autoCompactWindow`).
- Handoff arms (north#252): `north dispatch` writes `Arm: handoff-150k` (`handoff_arm_ctx`) or `Arm: no-handoff` as the first `Arm:` line of each fleet box's brief, alternating per tier until each arm has 30 launches there, and records it in the dispatch record; `north fleet launch` keeps the threshold on the session record, so a revived worker stays on its arm. On `handoff-150k` the session host messages the worker to land and hand off when its context reaches 150k, again per further 50k; `no-handoff` leaves it to Claude Code's compaction; the worker-handoff hook and `bin/capacity-watchdog` stay at 350k (`handoff_ctx`). `north worker-ledger --summary --by arm` compares the arms per tier. Once both arms hold 30 launches on a tier and each has a closed box in `north ledger summary --since 7d`, dispatch launches that tier on the arm with the lower cost per closed box (a tie keeps the handoff arm) and prints a north#57 recommendation note naming both costs.
- Pace notices: a pace hold or resume goes to the phone only (`PACE-HELD`, `PACE-RESUMED`); no fleet session is messaged, so a notice never wakes a session and never reads as an instruction to stop spawning (north#186, north#249). An idle session sees each account's pace in its next prompt through the grounding hook.
- Goal ETA: `agents plan` prints, per project target, the critical path over the goal's open boxes at the spawn gate's width with landing overhead, predicted finish against the target and n per box, and records it as a `goal_eta` calibration row ([feedback-loop.md](feedback-loop.md#goal-eta-north35-box-7)).
- `agents plan --score PROJECT` scores a passed project target from the open issue backlog, linked issue boxes and rolling seven-day run costs, prints on-date, in-budget and spec-pass, and appends one row to `~/.local/state/agents/goal-scores.jsonl`. Missing issue or spending evidence is unmeasured. Project share applies to available account dollars. Projected misses offer one budget/date/scope decision with recorded non-AI service costs and speedups.

## Fleet sessions

- Fleet sessions: `north fleet launch` registers the session's row in the fleet store's `fleet_sessions` table on the ledger host (`north fleet row register`) before it starts anything: a launch claims a name that no live session on another host holds, `--take-over` replaces the row under the name, and the launch refuses with the reason when the store refuses the name or the ledger host does not answer (a send never refuses for that). A host marked `pulls_spool` in `[hosts.NAME]` runs only the CLIs other hosts place on it and refuses every launch. `north fleet send` and `ask` message a session, `north fleet tree` shows parent links, and `north fleet revive` restarts a session. A send, report, gate notice or host-death alarm for a session another host runs is spooled and carried by the fleet ticks (see Fleet spool), and a launch may name as its parent any session in this registry or the cached fleet table. `north fleet tree`, `north fleet list` and `north fleet list --json --all` read the cached `fleet_sessions` copy the tick refreshes (never waiting on the ledger host) and list each session another host runs beside this host's own live records, which win over this host's own table rows, with their `host`, `machine` and `tasks` (marked stale after 5 minutes without an update and left out after 7 days), every tick also publishes this host's open decision gates into the store's `fleet_gates` table and caches the table beside the sessions, so `north gate list [--json]` and the issue-gate guard behind `north fleet launch` and dispatch show this host's gates beside the open gates other hosts hold (rows with their `host` and an id answerable as `HOST:ID`, read from the cached copy and never waiting on the ledger host), and `north gate answer HOST:ID N` (`--session NAME` only when the cached table lacks the gate) spools a GATE-ANSWER row naming the gate, the session (which the table must hold on HOST) and the calling session, which the asking session's host applies once by row id on its tick, so the answer reaches the asking session on its own host (north#184). `north gate open` for a session this registry lacks but the fleet table names spools a GATE row, which that session's host opens as a gate of its own, once by row id, on its `north fleet tick` (north#416); until a tick runs on the opening host the row waits in its spool. Each tick also revives the sessions a host reboot stranded: `north fleet rebooted [--revive]` lists this host's recently active sessions that are parked (not stopped, host process gone), were last written before the machine's boot time (`/proc/stat` btime), had been active within their idle limit at the boot (an older stream means the host parked itself) and did not end on a `Done:` report, and with `--revive` runs each through `north fleet revive` (placement kept, `--local` for a conversation on this host) and sends it `host H rebooted at T; resume from your last checkpoint`; `north fleet tick` runs it for its own host, so a rebooted host's sessions resume on the first tick after it boots, a revived session's record being written again so the next tick lists it no more, one that cannot be revived retries each tick, and a tick starts no new revive past 15 s so the 50 s unit is not killed between a revive and its message.
- Fleet store: `north fleet row put` reads one fleet row or an array of them as JSON on stdin and commits them to the threads ledger in one transaction, once per row id, printing `committed ID` per row; where this machine does not hold the ledger it forwards the rows over the threads ssh remote and answers the remote exit code. The ledger also holds `fleet_sessions`, one row per session name with the provider, account, cwd, parent, placement, machine and tasks `fleet list` shows, which a launch claims only while no session of that name is live fleet-wide (north#429).
- Fleet spool: every `north fleet send`, parent notice (`Fleet::tell`) and `ask` first writes a MESSAGE row to `fleet/spool/ID.json` (renamed into place). A recipient in this host's registry also gets the row handed in at once through `hand_in`, the one path that delivers a row into a session: it takes an exclusive lock on the session's `delivered` directory and creates `delivered/ID` before delivering, so a row id already there (the same row from a later tick) is a no-op, and a failed delivery clears the entry and withdraws the row from the spool. A name neither in the registry nor in `fleet/.fleet-sessions.json` (the cached copy of `fleet_sessions`, which each `fleet tick` writes on its own host and, through `north fleet spool cache`, on every far machine it pulls) fails at once; a name only in the cache is spooled for the ticks to carry, and the send names the host that runs it. A `job-run --notify` exit for a session on this host is handed in at once and otherwise waits in the spool. The tick delivers every MESSAGE, GATE, GATE-ANSWER and JOB-EXIT row addressed to a session on its host, a JOB-EXIT as the session's wake prompt, once by row id; JOB-START and JOB-BEAT rows stay in the store as wait leases. Each tick also marks exited every row of its host that its registry no longer holds, so a forgotten name is free again. A tick that pulls a far machine also asks it for its own registry (`north fleet spool registry`; gex45 keeps the legacy sessions launched there), publishes those sessions under that machine's host name, and hands the rows addressed to them in on that machine over ssh (`north fleet spool deliver`), once by row id in that machine's delivery journal. A JOB-EXIT that reached the store more than a day ago is no longer delivered. A session cannot be named `spool` (north#429).
- Fleet tick: `north fleet tick`, run every 30 s on each fleet host by the `fleet-tick` timer, makes one `north fleet row exchange` with the ledger host (over the threads ssh remote, or the local ledger on the host that holds it): it commits every row in this host's spool and withdraws a spooled row only once that exchange answered, and also takes the spool of every far machine whose CLIs this host runs (`north fleet spool take` over ssh on each machine a live session of this registry is placed on, plus each `[hosts.NAME]` with `pulls_spool = true` in the orchestration policy, never this host) and puts those rows through the same exchange, dropping on a machine (`north fleet spool drop`) only the ids that exchange committed (ids go on the command's stdin, so any count fits); a row the store refuses or this build cannot decode is set aside on its machine (`north fleet spool set-aside`) with a notice and never fails the pull, and a pull or drop that fails is recorded under the machine's name in the tick's `pull_failed` and printed as `not pulled from NAME` so a later check can skip that machine's lapse check for the tick, other machines are still pulled, and the ssh helper is `fleet/ssh.rs`, publishes this registry into `fleet_sessions` and caches the whole table in `fleet/.fleet-sessions.json`, and fetches the MESSAGE, GATE, GATE-ANSWER and JOB-EXIT rows addressed to this host's unstopped sessions (and its CONTROL rows, below) sent since each session's creation and within the 7-day row window. Each goes through `hand_in`, which skips an id already in the session's `delivered` journal, so a second tick delivers nothing; a parked session is revived under its start lock. The row id fixes the prompt's uuid (a hash of the id), so the CLI echo and the session host's unaccepted-prompt replay match the row by id whatever signing or urgent prefix the text carries; a `delivered/ID.handing` marker left by a tick killed mid-delivery is redelivered once unless the session host journaled or echoed that uuid. A row from this host is signed by its sender alone and one from another host as `sender@host`. Journal entries older than 14 days are pruned. The TUI desk, wait results, reboot notices and a closed gate's answer to its session send through the spool and `hand_in` too: the answer is a spooled MESSAGE row handed in by id at once, and one whose hand-in failed is delivered by a later tick (north#429).
- Fleet control (north#433, box 1d of north#429): `north fleet forget`, `stop` and `interrupt` of a name this registry lacks but the cached `fleet_sessions` table names write one CONTROL row (the verb in its text) to the spool and print `spooled CONTROL row ID`; a name in neither fails with `no session named NAME`. The tick on the host that holds the session fetches CONTROL rows for its stopped sessions as well as its running ones (a stopped session still receives no MESSAGE), and applies each once: `stop` and `interrupt` are journaled by row id in the session's `delivered` directory, and `forget` needs no journal because the session leaves the registry. `show` stays local-or-error.
- Placement gate: `north fleet launch` and `revive` of a Claude session run Claude-only placement first and print one verdict line per account (available with its headroom, or out at 95% 5h, a measured 5h burn over the 50%/h cap, or a provider-exhausted week; the pace controller's held or over never refuses). A code-only public box (declared `Surface:`, no local `Needs:`, repository north, wisp or makgora) is refused with the `north cloud launch` command for the account with the most headroom, run on the host where that account is signed in with that profile's `CLAUDE_CONFIG_DIR` (cloud compute has no separate charge and draws the account's plan limits; the credit is only an extra balance spent first), unless `--local "REASON"`; an account other than the one placement picks (the most headroom among the accounts that can run on the chosen machine, or here) is refused unless `--pin "REASON"` or it ranks with that account given 5 more points of its own week room under the same spend target, so a near-tie keeps the named account (north#389).. A box needing something local (private stores, native clients) runs on the first `[hosts.NAME]` machine with `ssh` whose `serves` covers each need, a `NEED` for every repository or a `NEED:REPO` for one, and that is below its resident cap and not saturated (a host is skipped, with the reason printed, when its available memory leaves no room for a session (the unattended memory floor beside the agent class's 768 MiB request) or its root disk is under `build_disk_free_gib`, never for its build queue or its load, because sessions are admitted on memory and slot room only; the reading is taken over the same ssh and cached for 60 s, and `agents plan --place` applies the same rule; `--cwd HOST:PATH` onto a saturated host is refused unless `--pin "REASON"`); failing that it stays here when this host's own `[hosts.NAME] serves` covers its needs, and is refused as unserved when it doesn't. The reasons are recorded on the session and shown in `north fleet list`. `--test` sessions skip the gate. A launch claims, before it starts, every issue it holds (`--task REF`, else all those the first `Item:` line names up to a word such as `follows` or `see`, in the prompt or the brief it points at; the first is the session's task and `fleet list --json` shows all as `tasks`), refusing on a live claim and taking one a stopped session left, and releases them when the session ends or fails to start. A `--task REF` or `Item:` launch is refused while a running fleet session on this host, any other host (over ssh, or the laptop's copied list) or a dispatch launch of the last two hours already holds REF, unless `--force-dup "REASON"`, which is recorded as `dup: REASON`.
- Launch tier (north#242): `north fleet launch` of a Claude session that holds an issue (`--task REF`, else the brief's first `Item:` line) reads the brief's `Category:` and facets (`Spec`, `Surface`, `Verify`; a missing Category is `feature`), routes them as dispatch does (art on sonnet-high, mechanical on worker-haiku with its miss retried on sonnet-high, feature, tooling, native-check, balance-tuning and bug-known-cause alternating the Sonnet and Opus arms until the ledger holds 15 runs of each and then taking the arm with the lower `north ledger summary --since 7d` cost per closed box, everything else on worker), starts the session with that tier's `--model` and `--effort` from South's `[tiers]` table, and writes the `Tier:`, `Arm:` and `Follows:` lines into the prompt's brief header (a Haiku pick also gets the wait-on-Monitor rule). A brief that already carries `Tier:` (a dispatched box's, or an escalation's `worker-sonnet`, `worker-high` or `worker-xhigh`) keeps it, and a `Tier:` naming no tier is refused. A `--model` of another family than the pick is refused unless `--tier-reason TEXT` is given or the brief carries a `Tier-reason:` line, and a Claude launch that holds no issue is refused any `--model` without one, since no issue's routing can check it. Such a launch with no `--model` is routed the same way on the `Category:` (or `Tier:`) line in the header block (the lines before the first blank line) of its system prompt, prompt or named brief, with the session name standing in for the item; a header that marks a worker (`Delegation: role=worker`, or a `Spec:`, `Scope:`, `Surface:` or `Verify:` line) but declares neither and names no `Item:` is refused, and a brief whose header does neither keeps the account's default, so a plan's per-box lines below the header route nothing; the reason is recorded on the session as `tier: TEXT` beside `--local` and `--pin`, shown in `north fleet list` and kept by `revive`. Each launch is appended to the launching host's `launches.jsonl` as a hand launch, which dispatch on that host counts for arm alternation, Haiku retries and `Stop: decision` reports and which holds nothing; a hand launch on another host reaches dispatch only through the ledger's runs.
- Learning tick (north#112): `north tune [--dry-run]` prints the `north ledger summary --since 7d` dashboard line, then decides from the ledger's closed boxes of the last 7 days the cells briefs and routing take: `route CATEGORY` (the arm dispatch takes once both arms hold 15 runs and a cost per closed box), and `eta_minutes FAMILY CATEGORY` and `budget_usd FAMILY CATEGORY` (the ceiling of the p75 run wall and twice the median cost per closed box, as briefs print them). It writes them to `~/.local/state/north/tune/cells.json`, whose `route` cells dispatch and `north fleet launch` follow while the file is under 36 h old, and appends one line per new, changed or dropped cell to `provenance.jsonl` there with its from and to values, the ledger rows and closed boxes behind it, the 95% order-statistic interval of its figure and the rerun command. Each tier and category whose cost per closed box rose more than 25% over the 7 days before, on a tier that started a worker run in the last 7 days (a box is labeled by its first run's tier, so a retired tier's late closers file nothing), gets one north issue titled `Cost per closed box rose more than 25% week on week in TIER CATEGORY`, unless an open issue of that title holds it, and the last line is the open north issue count. `--dry-run` writes and files nothing.
- Bet dividends (north#112): `north ops dividend [--dry-run]` reads each open issue labelled `bet`, takes the `north ops dividend CHECK` commands its Dividend section names, evaluates them over the last 7 days, comments `north ops dividend DATE: PAYING` or `DECAYED` on the issue once a day, and sends the proxy a fleet message for each bet that comments DECAYED. The checks are `cloud-lane` (a cloud placement in the last day while the cloud credit lives), `laptop-share` (the laptop under 80% of measured CPU-hours from each host's capacity usage log), `game-share` (makgora and wisp at least 60% of safe-push landings) and `release-closed` (makgora `priority:now` issues closed at least one a day). `north ops dividend CHECK` prints one verdict and exits 0 paying, 1 decayed, 3 unread; a check whose input cannot be read is UNREAD and comments nothing.
- Ops check (north#112): `north ops check [--dry-run]` (timer every 5 minutes on Nexus, and on one other host for the dead-man) reads `north-data/expectations.toml`, built into the binary: each `[[expectation]]` names a measure (`cloud_launches`, `launch_failures` from the dispatch record, `closed_boxes` from the ledger, `heartbeat_age_minutes`), a threshold and `breach_when` direction, a window, an owner, the deterministic fix it should become, the host role it runs on (`nexus` or `elsewhere`) and optionally an `until` date. A new breach pushes the phone through `nexus-alert` and messages the `[notify] proxy` session once, a standing breach stays quiet, and the clear sends one `cleared`; a failed phone push is tried again next tick, and an unreadable measure fails the tick and leaves that state alone. Each tick writes `ops/heartbeat.json` under the agents state directory; `nexus-heartbeat` breaches when Nexus's is older than 15 minutes, and `nexus-dead-man` reads it over ssh from another host. `--dry-run` prints every expectation's state and sends and writes nothing. Tests replay a breach and a clear for every shipped expectation.
- Dispatch: `north dispatch [--dry-run]` (Nexus timer every 5 minutes, south `modules/north-dispatch.nix`) keeps free worker slots busy. It prints each `[hosts.NAME]` (the laptop only while `north laptop status` says available, counting its sessions from the fleet list it copies to Nexus) with its resident cap and running sessions, each pace-control account as open or out with the hosts `[accounts.PROVIDER] profiles` signs it in on (less this host when its roster has no login of its own for the account), and per host and account the free slots: cap − running for an open account, none for one the out-rule holds (5h at 95%, 5h burn over its cap or the week exhausted; pace's allowed workers and projections never hold). It never runs replays; `north policy-replay sweep` does, weekly from the Monday tick and on each new model release `model-watch` reports. The `agent-config-check` rules group requires every `rules.toml` entry to carry a `placement` (`global`, `merged:<id>`, `skill:<name>`, `hook:<name>` or `dropped`), matches the `global` entries 1:1 and in order with the AGENTS.md bullets, and fails an entry added since the landed `origin/main` copy unless it cites at least 2 ids in `incidents.jsonl`. `safe-push` runs the same sha256 lookup at landing: a change that alters `agents/AGENTS.md` is refused unless the pushed tree carries an `agents/replay/sweep-*.jsonl` row for the new sha256 with 3 or more trials on every `agents/replay/*.json` scenario, and the refusal prints the `north policy-replay sweep` command and its measured cost (about 9 minutes and $2 at list price); a change that leaves `agents/AGENTS.md` alone is untouched.

[--trials N] [--jobs N] [--policy AGENTS.md] --out RESULTS.jsonl` runs scenarios from `south:agents/replay/` × arms × trials, at most 4 in parallel, through `claude -p` with each policy arm (`full`, `minus:PREFIX,...`, `minus-file:PATH` with one rule prefix per line, or a scenario arm name) appended in place of the live `~/.claude/CLAUDE.md` (`--setting-sources project`, empty cwd). It scores each run with the scenario's regex or tool-call detector, appends one jsonl row per run (pass, turns, input/output/cache tokens, model, effort, wall seconds, `leftover_processes` (processes carrying the run's `POLICY_REPLAY_RUN` tag still alive after scoring, then sent SIGTERM and SIGKILL after 3 s before the temp dir is removed) and `cost_api_usd_comparison` as an API list-price comparison only) and prints pass rate per scenario × arm. `north policy-replay sweep SCENARIO.json... --variants VARIANTS.toml [--variant NAME...] [--provisional]` instead runs every `[[variant]]` of `south:agents/replay/variants.toml` (built from the live AGENTS.md, or the file a `policy` key names, by `minus`, `minus_file`, `plus` text files and `placement` moves to a skill or hook) over the scenarios × trials, appends per-run rows to `~/.local/state/agents/replay/sweep-<UTC date>-runs.jsonl` and one row per variant to `south:agents/replay/sweep-<UTC date>.jsonl`, which lands with the policy so every host's `agents sync` finds it, (policy sha256, startup tokens on the `agents sync` session-start chars/4 basis, conformance, n, tokens per run, `usd_or_null`, wall seconds, model, effort), and writes the candidate `~/.local/state/agents/replay/operating-point-candidate.toml` (`--candidate PATH`): the fewest startup tokens among variants with no one-sided Fisher drop (alpha 0.05) from the best variant overall or per scenario and no 3/3 to 0/3 scenario flip, with its per-scenario counts; it never touches `south:agents/operating-point.toml`. Re-run it on a model release, a big policy change or weekly. `north policy-replay promote SCENARIO.json... [--candidate PATH] [--operating-point PATH]`, run in a south worktree and landed through `safe-push`, copies the candidate's point keys into the operating point and keeps every other key and comment (`weak_scenarios`); it refuses a candidate that misses a listed scenario, flips a scenario the current point passed every trial of to 0 passes, or whose conformance is significantly below the current point or the frozen anchor (`anchor_conformance`, `anchor_n`, `anchor_date`, the point the promotion chain started from), so small steps cannot compound. `--accept-drop REASON` on `promote` (a model release, a new scenario set) skips those checks, records `accepted_drop` and `accepted_drop_date` and re-anchors on the candidate. Per-run model arms: `--model sonnet|haiku|opus|<full id>` and `--effort low|medium|high|xhigh` override the scenario's model and effort, and `--advisor MODEL` passes `claude -p --advisor MODEL`; Fable is refused as either, and `--sweep` refuses all three. Each row then records `model`, `effort`, `advisor`, `advisor_calls` (distinct `server_tool_use` blocks named `advisor` in the stream), `advisor_model_resolved`, the advisor's input/output tokens and `advisor_usd` from the result's `modelUsage`, and `usd` with `usd_basis` (the result's list-price `total_cost_usd`, since the north worker-ledger rate needs weekly usage readouts bracketing the run). A `command` detector runs the scenario's shell command in the run's cwd after the agent finishes and before the leftover-process kill, passing on exit 0 within its `timeout_s` (default 120). ## Machines, capacity and scheduled jobs

- Product verification: `verify-north` builds north from the checkout around the current directory (or takes `--north PATH`), then in a 160x45 tmux terminal opens `north fleet`, launches a Claude haiku session from the Ctrl+N form, checks an Alt+U urgent answer within 10 s during a running `sleep 120`, a Ctrl+G deepen run in the ledger, a Codex `fleet ask`, and a `north task check` verdict; a separate cleanup process forgets its sessions, kills its terminal and asserts none of its session hosts or app-servers survive, even when the run is interrupted. One line per step with wall ms; nonzero exit on any failure.
- Fleet landings: fleet exports `NORTH_FLEET_SESSION` to every command a session runs, `safe-push` logs that name in `pushes.tsv` with the default-branch commit it landed, and north records that commit as the landing of the session's task (its `--task`, else the session name) when each turn ends and every 30 s while the fleet screen is open, so `north task landed` is optional.
- Fleet receipts: `north fleet launch` makes the calling session (`NORTH_FLEET_SESSION`) the parent, or, for a launch from outside the fleet (dispatch, timers, a bare terminal), the `proxy` session when it lives here or a relay reaches it, unless `--parent NAME|none` says otherwise; such a launch does not hold for admission unless it passes `--wait`. A launch that holds for a saturated host gives up after 2 minutes, exits non-zero with the reason and queues one `Not done:` message to its parent so the lead restaffs or pins at once. When a child ends a completed turn that landed a commit or whose reply starts with Done, Not done, Split, Stop or Blocked, its session host queues one message to the parent: `[from NAME · turn N · exit E · landed SHA]` and the child's reply, cut at 4,000 characters with a pointer to `north fleet show NAME`. Other completed turns (progress lines, questions) stay in the child's transcript and ledger without waking the parent; `north fleet show NAME` shows them. A failed turn is queued like any receipt with the last 5 transcript lines, while a host death mid-task is sent urgently, which a per-child `fleet watchdog` process notices. A gate the child opens also goes to the parent as one line. A gate opened with `--issue OWNER/REPO#N` decides that issue: while it is open, here or on a relayed host, `threads ready` leaves the issue out, dispatch holds it and `north fleet launch` refuses a brief naming it, quoting the gate id (north#370). The parent or Tom can close it with `north gate answer ID N [--note TEXT]`; the ledger records the answering session name (or `tom`), and the child receives a `[gate ID]` fleet message with the chosen option and optional note. A closed gate never defaults later. A stale answer shows the stored answer and answerer as information. Launch test sessions with `north fleet launch --test`; their children inherit the marker and their gates stay out of Tom’s decisions digest. `verify-north` marks its sessions automatically. The ledger's `receipts` table claims each notice once, so restarts never resend one; a stopped parent is never revived for a notice.
- Runtime promotion: `north runtime update` (run by each `north agent-runtime-update` pass) fetches north main and, when `~/.local/state/north/current` is behind origin/main, builds it in one detached `worktrees/runtime-build` lane reused for every commit (the dev shell keys `RUSTFLAGS` on the checkout path, so a per-commit path would recompile every dependency) under a `runtime` capacity lease (front of the queue, never deferred by load, disk or heavy leases) (while this host is in game-reserve it instead prints `north runtime: building <short> on HOST while this host is in game-reserve`, runs `north runtime update` on the first other `[hosts.NAME]` with room by the `north capacity offload` rule and rsyncs that host's programs back, so the game never waits out a build), installs `runtimes/<sha>/north`, `verify-north` and `tree/` (a `git archive` of that commit, which scheduled jobs run harness code from), swaps `current` atomically, runs `north runtime health` and `agents sync` (each bounded to 5 minutes; `git fetch` to 2 minutes) (which projects skills, scripts and hooks from the new `tree/`, so they change only when `current` does) and swaps back if either fails, alerting the proxy; every host runs it from its own `north-runtime-follow` timer every 2 minutes, and returns before building, exporting or rooting when `current` already names origin/main; a commit whose build, health or sync failed is held back for an hour (`runtime-failed` names it), so the timer neither rebuilds it nor alerts again until then, while a deferred build (exit 75) retries on the next tick, and so does a build that capacity admission or its systemd scope stopped before cargo ran (the build passes `--timings`, and a failure that left no `cargo-timings/cargo-timing.html` newer than the build start is a refusal, not a broken commit); it keeps the previous runtime plus the 3 newest others and holds `runtime-update.lock`. Promotion roots each store path the binaries name as `runtimes/<sha>/gcroot-<store name>` (`nix-store --add-root --indirect`), so Nix garbage collection never removes what a promoted runtime loads and pruning a runtime releases its roots. A build is abandoned when `origin/main` moves past its commit (checked every 20 s; `NORTH_RUNTIME_WATCH_SECONDS` overrides) while it has run no more than half the last local build's wall time (`runtime-build-seconds`): its process group is stopped and `north runtime update` restarts on the new head. A build past that half is finished and promoted, and the same run then builds the new head, up to 5 passes before exiting 75, so landings that arrive faster than a build still move every host forward instead of livelocking. A host builds a runtime only when no other host has one: `north runtime update` first pulls `runtimes/<sha>/north` and `verify-north` from each other host with an `ssh` or `deploy_ssh` destination over rsync and runs `nix-store --realise` on their store references (a pulled runtime that fails either step is discarded), then builds locally; a host whose `[hosts.NAME]` sets `builds_runtime = false` (Nexus) never builds. A host that can neither pull nor build origin/main (it does not build runtimes, its game-reserve offload found no room, or its capacity lease deferred the build) reads each peer's `current` over ssh and promotes the newest one that is an ancestor of origin/main and ahead of its own, printing `north runtime: <main> is not built anywhere yet; catching up to <short>, promoted on HOST`; it exits 75 only when no peer is ahead. `north runtime deploy HOST...` builds that runtime on the machine it runs on (the laptop, so Nexus's 3 cores never compile north), runs `nix-store --realise` over its store references on each HOST, rsyncs the programs into the HOST's `runtimes/<sha>/` and runs the shipped `north runtime update --sha SHA` there, which waits up to 10 minutes for that host's `runtime-update.lock`, skips its build and promotes exactly that commit. Each deploy step prints what it waits on (the `runtime-update.lock`, the build, `nix-store --realise`, the copy, the remote `north runtime update`) and is stopped with an error naming the step, the host and its limit (30 min for the lock, 10 for realise and copy, 15 for the remote promote; `NORTH_RUNTIME_STEP_SECONDS` overrides them), so a stuck deploy fails with its reason instead of hanging. `north runtime deploy` with no HOST ships to every other `[hosts.NAME]` that has an `ssh` destination and attempts the rest when one fails, except that a host which sets `builds_runtime = false` (Nexus) is shipped to only by a host that sets `settles_fleet = true`: elsewhere (gex45 has no ssh route to Nexus) it is left out of the plan, and the deploy prints `north runtime deploy: skipping nexus: it builds no runtime, and the host that settles the fleet ships to it`. After a landing on north's main branch, safe-push runs `north runtime follow --repo-dir DIR`; for a repository whose origin is `north` it starts `north runtime promote` (`runtime update` here, then `runtime deploy` to every declared host) in the background, logging to `runtime-follow.log`, so a landed change reaches `~/.local/state/north/current` on each fleet host with no manual step. On the host whose `[hosts.NAME]` sets `settles_fleet = true` (the laptop, the one host that reaches gex45 and Nexus), `north runtime update` runs `north runtime settle`: it updates here, ships its runtime to each deploy destination whose `current` differs, then probes every host over one ssh script for its live runtime, `capacity-watchdog.service` and `north-runtime-follow.timer` state, its north process count against `landing_north_processes_max`, and every absolute path a hook command names in `~/.claude/settings.json` and each non-stale profile `settings.json`, printing `north runtime settle: HOST: live and healthy` or its problems and writing `runtime-settle.json` with its CPU pressure avg60 and load per core recorded but not judged, since host overload is the capacity watchdog's to report. Each landing is judged once, on the first tick at least `landing_live_deadline_sec` (600) after it landed (`runtime-settle-judged` names it): a host whose runtime is not that commit or a descendant, or any problem, reopens the landing's `(north#N)` issue with the problems as a comment and fleet-sends them to the proxy and every session whose tasks name that issue. `agents sync` refuses to activate a generation that lacks a hook still registered under `~/.agents/hooks/` in those settings files, naming each missing hook and the file that registers it, and keeps the current generation.
- Orphan lease reaper: `north capacity reap-orphans` stops the scope of every run lease whose wrapper process is gone, so no Warcraft client or run outlives its runner and the lease's slot frees; it is the stop half of the laptop's `laptop-auto` tick and needs no `laptop` command, so gex45, which has no such tick, runs it from the `lease-reaper` user timer every 30 s (south `modules/lease-reaper.nix`, imported by `hosts/gex45/configuration.nix`) (north#191, north#335).
- Capacity estimates: `machine-capacity estimate [--json] [--class CLASS] [--owner OWNER] -- CMD ARG...` uses the current directory and the last 20 matching measured runs, with exact signature, full owner/shape, owner prefix/shape/class, family/repo, family (none for unrecognized `other` commands), and declared-class fallbacks. An expensive target absent from exact family/repo/package history stays heavy (native for native clients) with low confidence, even when other targets have family history; known targets and cheap families retain nearest matching. Imported rows without exact targets cannot establish that a target is known. Owner levels require an explicit owner; the prefix is its leading ASCII letters. It prints p50/p90 cores, peak memory, I/O bytes, disk busy share, sample count, match level, and confidence. Disk busy share is the maximum physical whole-disk `/proc/diskstats` I/O-millisecond delta divided by run wall milliseconds (host-wide; partitions and virtual devices excluded). Stored cgroup I/O pressure is reference data only. Runs without a class reserve rounded-up p90 cores and p90 memory plus 20%; running batch CPU accounting uses the greater of measured two-minute use and estimate p50, plus 25%. ## Wisp payoff

`north wisp payoff [--since YYYY-MM-DD] [--json]` reads retained Mak'gora evidence, Wisp state, and Wisp evidence/build directories without creating a store. It prints per-kind UTC Monday weeks, completed comparison agreement, invalid native attempts, native client-minutes, Wisp main commit counts, retirement candidates, and disagreement evidence paths. JSON includes each contributing run for audit. The fleet Ctrl+T digest refreshes its summary in background upkeep.

Pad families use their script directory (standalone pads use their name). Pad client-minutes count two clients over game, reset, reload and run time; Wisp, comparison and wait time are excluded. Acceptance report elapsed time is divided equally over checks and marked estimated. Batch dates use file modification time because the format has no timestamp. PASS and FAIL count as comparisons only when both headless and comparison ran; INVALID never counts as disagreement.

Retire candidates have at least ten agreeing comparisons and zero disagreements across the last fourteen days, independent of the display filter. They select Wisp-only evidence with a one-in-ten native sample. The weekly projected sample saving is 90% of those kinds’ historical native minutes, a counterfactual estimate. Actual avoided minutes, closed Public 0.1 boxes, native minutes per closure and Wisp-only closure shares remain unknown when retained evidence lacks closure provenance and skipped-run records. Do not equate projected savings with observed payoff. The command never files issues or sends messages; its evidence paths support deduplicated issue filing and planner handoff.

The planner contract is `schema_version: 1`. `families[]` is computed from the full rolling fourteen-day window even with `--since`. Each entry has `id`, `match_rule: {kind, values}`, `verdict` (`wisp-only` or `native`), `native_sample_rate` (0.1 or 1.0), `counts`, and inclusive `window_start_unix` / `window_end_unix`. `parent-directory` matches an immediate POSIX dirname in `values` and a `.pad` basename; `exact-path` matches a whole path in `values`; `none` applies to accept checks, not scripts. Unknown or ambiguous matches select native. Paths are repo-relative POSIX strings; reject absolute paths, backslashes, and dot segments. Headless-session batches are excluded regardless of their comparison message.

Sampler `sha256-first-u32be-mod10-v1` hashes UTF-8 `scriptPath + "\n" + fullSourceRevision`, without a trailing newline. Interpret the first four SHA-256 bytes as an unsigned big-endian integer and take modulo ten. Select native when the verdict is `native` or that bucket is zero. JSON `sampler` carries the identity, exact input description and a test vector. This gives identical reruns the same sample and prevents display filtering from changing routing.
