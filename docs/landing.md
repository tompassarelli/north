# Landing a change

A change reaches main through the lander, which checks the exact tree it pushes. Agents edit in `~/code/<project>/worktrees/<slug>`, never in `main/`, and land with `safe-push --to main` (the north binary entered through its `safe-push` link, [crates/north-safe-push](../crates/north-safe-push); `safe-push --help` is the full contract; the [repo-safety skill](../harness/skills/repo-safety/SKILL.md) is the procedure). The "Landing and lanes" entries in [features/04-landing-and-lanes/](features/04-landing-and-lanes/) describe each gate. A worker is briefed first: [briefing.md](briefing.md).

## The path

1. **Enqueue.** While a landing freeze is placed (`north land freeze --cause TEXT`, which writes it on this host and, over ssh, in every fleet host's state home for each login the lander reads there), `north hand-in`, `north finish` and `safe-push --to main` refuse at once with the freeze's cause, before any check runs and before a ticket is written; `north land freeze --lift` lifts it everywhere ([crates/north-landing/src/land/freeze.rs](../crates/north-landing/src/land/freeze.rs), north#1281). `safe-push --to main` decides its route, which refuses any host that is neither `landing.lander-host`, nor an ssh host of the fleet's `[hosts]`, nor in `landing.remote-hosts`, and any `landing.queue` other than the lander, naming the setting to add. Otherwise `north land enqueue` runs the outgoing scans and the land checks the lane adds, squashes the lane to one commit unless `--several-commits`, and queues it, printing the seconds each step took (`safe-push: timings:`). The private-kind judge reads the squashed head once, beside the last gates; a public lane whose judge is still asking queues with that verdict outstanding, and the lander lands it only once a passing verdict on that head is in ([private-text-judge](rationale/private-text-judge.md)). A lane that crosses a trust boundary and holds no reviewer accept of its patch queues held under that patch id, and the lander keeps it out of every candidate until the review-accept and safe-push-keys scans pass on the head it lands. The lander makes one security read of the held patch itself, a stateless one-shot model call under the commit reviewer instructions read at main with the lane as data, and records an accept of that patch id only when the answer opens with `ACCEPT` alone; any other answer, error or timeout refuses the ticket with the answer, and a ticket held past two hours is named once to the coordinator ([crates/north-landing/src/land/unreviewed.rs](../crates/north-landing/src/land/unreviewed.rs), [crates/north-landing/src/land/security_read.rs](../crates/north-landing/src/land/security_read.rs), north#1632, north#1650). The worker reports `Done: queued <branch>` and ends its turn.
2. **Plan.** The lander (`north land serve`) takes the queued lanes, urgent first, and plans candidates that are each origin/main plus a prefix of them, one per free build slot, building each on its own worktree.
3. **Check.** It runs the checks the repository's committed [.safe-push](../.safe-push) maps to the changed paths (`land.check` entries) through `safe-push --check-candidate`, sending each where it can run: with a `land.workflow`, every check except the `land.local-only` and `land.machine-bound` ones runs as one GitHub Actions job through `north land actions`; machine-bound checks run on the `land.runner` build host, the one holding the checkouts beside it; a check that reads one before it lands, such as the operator schema check of the south checkout (north#1281), is both a `land.check` and a `land.machine-bound` line, so it refuses the lane before it lands rather than after; and a host in game-reserve ships the candidate to another host with room (`north capacity offload`).
4. **Refuse.** It refuses a lane for a failing check, a conflict or dropped commits, a secret (betterleaks) or a privacy leak (deny-list, commit email, native item references). Every other gate follows `landing_refusals` in [harness/defaults.toml](../harness/defaults.toml) and in `shadow` logs its would-be refusal and lets the lane land ([landing-refusals-shadow](rationale/landing-refusals-shadow.md)). Test admission refuses on every landing path. The lander never force-pushes.
5. **Land.** It pushes the largest green candidate to main, the exact tree that was checked, tells each lane's session it landed, and runs the after-landing checks (`land.after`) and `north follows-release`. Its follow keeps `north follows-release` on the lander's host; the runtime follow, the after-landing gates, the graph ingest and the build-ahead requests run where `post_landing_host` in [harness/defaults.toml](../harness/defaults.toml) places them, which on a lander's host that is no build host is a build host reached over ssh under the operator login, and nowhere, with a line in the follow log, when none answers (north#1553). The landing reads no issue: a commit's `Item:` and `Box:` trailers stay in its message, and the landing neither checks them against an issue nor ticks a box or closes an issue (north#1650). A red after-landing run reverts only the lane that broke it. A `land.after`, `after-landing.check` or `after-landing.advisory` command that is no `land.check` needs a `land.after-only = REASON :: COMMAND` line, and the "after-only reason" lane gate enforces it.

`safe-push --dry-run --to main` runs the same scans and land checks on this host without queueing.

## After the push

CI runs on main ([.github/workflows/](../.github/workflows/)). No workflow re-runs or blames a failed run any more: the "Main is red" workflow was retired with the fleet governance it served (north#1650), so a red run waits for whoever reads it.
